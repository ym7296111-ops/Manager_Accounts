# Runbook — إعداد المشروع وأول مالك

هذا الدليل يغطي مشروع Supabase جديدًا بعد تطبيق الترحيلات. لا توجد خطوة bootstrap منفصلة أو كلمة مرور أولية في GitHub Actions: إنشاء الحساب الأول يتم من تدفق التسجيل في التطبيق، بينما قاعدة البيانات وحدها تسند الدور.

## 1. تطبيق المخطط

1. اربط المشروع الصحيح بـ Supabase CLI وشغّل `supabase db push --linked` أو راجع خطة النشر التي يعرضها workflow قبل تطبيقها.
2. تحقق من نجاح migrations، وخصوصًا `20261016000000_first_signup_admin_and_retire_ci_backups.sql` و`20261016120000_add_owner_role_and_grant_all_permissions.sql` و`20261017000000_add_user_approval_workflow.sql` و`20261017010000_protect_original_owner.sql`. انشر أيضًا `supabase functions deploy approve-user`، وتحقق من توفر `SUPABASE_SERVICE_ROLE_KEY` للدالة فقط وليس للمتصفح.
3. جهّز عنوان التطبيق ومتغيرَي المتصفح `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY` وفق `.env.example`. لا يحتاج التسجيل إلى `service_role` أو بيانات bootstrap.

## 2. تسجيل المالك الأول

1. أبقِ التطبيق وتدفق التسجيل متاحين فقط للمالك المقصود حتى يكمل التسجيل الأول. قاعدة البيانات لا تستطيع التحقق من هوية مالك المشروع؛ **أول حساب Auth يُدرج حين يكون `auth.users` فارغًا يحصل تلقائيًا على `owner`**، ويؤكَّد بريده ضمن معاملة التسجيل.
2. افتح `/login`، واختر إنشاء حساب، وسجّل بريد المالك وكلمة مروره الشخصية.
3. سجّل الدخول بعد نجاح التسجيل. لا يلزم إجراء SQL أو استدعاء RPC لمنح الدور.
4. تحقّق تشغيليًا من ظهور ملف المالك النشط ودور `owner` في إدارة المستخدمين أو عبر استعلام قراءة مخوّل. لا تسجّل كلمات المرور أو مفاتيح Supabase في سجل التغيير.

يُحسم ترتيب التسجيلات ذريًا في قاعدة البيانات، مع فحص أن جدول `auth.users` كان فارغًا قبل إدراج المستخدم الأول. أي حساب لاحق يبقى `pending` دون دور حتى يوافق عليه المالك أو مدير النظام؛ عند الموافقة يُمنح `viewer` ويؤكَّد بريده. قيم `user_metadata` مثل `role` أو `is_super_admin` لا تؤثر في الدور، ولا توجد RPC عامة لمنح دور محمي.

> لا تفتح التسجيل العام قبل تسجيل المالك المقصود. هذه قاعدة تشغيلية لحماية التأسيس وليست تحققًا من ملكية الحساب، ولا تُعرض للمستخدم في شاشة التسجيل العامة.

## اعتماد المستخدمين التاليين

من حساب `owner` أو `super_admin`: افتح الإعدادات ← إدارة المستخدمين ← «المستخدمون المعلقون»، واختر اعتماد أو رفض بجانب الحساب. مثال برمجي (بجلسة المسؤول):

```ts
await supabase.functions.invoke('approve-user', {
  body: { userId: '<uuid-of-pending-user>', action: 'approve' },
});
```

تتحقق الدالة من JWT على الخادم، وتعيد RPC التحقق من دور المنفذ وحالة الهدف. لا تستدعِ `admin_approve_user` مباشرةً من المتصفح؛ صلاحية EXECUTE مقصورة على `service_role`. تأكّد من سجل `audit_logs.metadata.event` بعد كل عملية. يُعتمد جميع المستخدمين السابقين مرة واحدة عند الترحيل، ولا يُعاد اعتماد مستخدم مرفوض عند إعادة تشغيله.

### حماية حساب المالك

بعد تطبيق `20261017010000_protect_original_owner.sql` لا يمكن لـ `super_admin`
أو `service_role` أو RPC سحب دور المالك، أو تعليق حسابه، أو تغيير حالة اعتماده
أو حذف `auth.users` الخاص به. يظل بإمكانه تسجيل الدخول وتحديث تفضيلات ملفه
الشخصي العادية. تُرفض المحاولات بخطأ `42501` وتظهر في **سجلات PostgreSQL**
كـ `owner_protection`، لا في `audit_logs`: رفض المعاملة يُرجع معها أي إدراج
تدقيق داخلها. راقب السجلات عبر مشروع Supabase؛ ولا تعطل Triggers كإجراء
إداري اعتيادي. حساب مالك قاعدة البيانات/المشرف الأعلى خارج هذا الحد الأمني؛
احمِ الوصول إليه وراجع عملياته على نحو مستقل.

الترحيل السابق `20261017000000_add_user_approval_workflow.sql` منشور بالفعل؛
لذا أُضيفت الحماية في ترحيل أحدث قابل للتطبيق للأمام بدلاً من إعادة تسمية
الترحيل القديم أو تغيير سجله.

## 3. المشاريع القائمة قبل هذا الترحيل

عند تطبيق الترحيلات على مشروع قائم، تُغلق حالة التسجيل الأول بدل ترقية تسجيل جديد دون قصد. ترحيل `20261016120000_add_owner_role_and_grant_all_permissions.sql` ينقل إسناد `super_admin` الأول المسجل (أو أقدم إسناد قائم في مشروع قديم) إلى `owner` مرة واحدة؛ تبقى بقية إسنادات `super_admin` كما هي، ولا يُرفع أي تسجيل جديد تلقائيًا. استخدم حسابًا إداريًا قائمًا لإدارة الأدوار؛ وإذا لم يعد هناك أي مسؤول صالح، أوقف التسجيل واتبع إجراء استرداد خاضعًا لمراجعة مالك قاعدة البيانات بدل حذف علامة الحالة أو تجاوز الحارس.

## 4. تطوير محلي

1. شغّل `supabase start` ثم `supabase db reset` لإعادة إنشاء قاعدة محلية فارغة وتطبيق migrations وseed المحلي.
2. شغّل `npm run dev` واضبط `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY` محليًا.
3. من `/login` أنشئ أول مستخدم محلي. في قاعدة محلية جديدة يحصل هذا الحساب على `owner`؛ بقية الحسابات تنتظر الاعتماد ولا تحصل على دور قبل الموافقة.

لا تستخدم `supabase db reset` على مشروع سحابي. لا تضع كلمات مرور ثابتة أو مفاتيح خدمة في ملفات الإعداد.

## 5. QA accounts

قبل إنشاء أي حساب QA — سواء عبر لوحة Supabase Auth أو `scripts/sql/test-account-bootstrap.sql` — سجّل المالك المقصود أولًا. يفحص السكريبت حالة `first_user_id` ويرفض المتابعة إذا كان حساب `qa.*` قد استهلك تسجيل `owner` الأول؛ لا يحاول ترقيته أو خفضه إلى `admin`. إذا حدث ذلك بالفعل، أعد تهيئة مشروع QA المعزول وسجّل المالك المقصود أولًا، ثم أنشئ حسابات QA بكلمات مرور عشوائية خاصة ببيئة معزولة فقط.

## 6. النسخ الاحتياطي

لم يعد هناك GitHub worker أو طابور نسخ مخصص في التطبيق. صفحة `/settings/system/backup` تعرض معلومات وروابط لإعداد **Supabase native backups** من لوحة المشروع؛ تعطيل العامل لا ينقل ملفات النسخ القديمة تلقائيًا إلى Supabase. تحقّق من أي بيانات قديمة في bucket `private-backups` قبل تنظيفها يدويًا، وفعّل خطة النسخ المناسبة من Supabase Dashboard → **Database → Backups**.

## 7. GitHub Production environment

يستخدم workflow الترحيلات القيم التالية فقط:

- `SUPABASE_ACCESS_TOKEN` كـ secret.
- `SUPABASE_DB_PASSWORD` كـ secret.
- `SUPABASE_PROJECT_REF` كـ variable أو secret.

راجع `scripts/configure-production-environment.sh --check` لعرض أسماء المتغيرات والأسرار الموجودة، و`--apply --project-ref <ref>` لإعداد قيم الترحيل. لا تطبع الأسرار أو تضعها في ملفات المستودع. لا يحتاج تسجيل المستخدم إلى أي من أسرار GitHub هذه.
