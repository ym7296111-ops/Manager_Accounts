## 0. الخلاصة (30 ثانية)

1. **السبب الجذري لعدم ظهور المسجلين (ثقة عالية):** استعلام قائمة المستخدمين يدمج الجدول `user_roles` داخل `profiles` **بصيغة غامضة** (`user_roles(roles(...))`)، بينما يوجد **مفتاحان أجنبيان** من `user_roles` إلى `profiles` (`user_id` و`granted_by`). PostgREST يرفض هذا الدمج بخطأ **`PGRST201`** (HTTP 300) فيفشل الاستعلام بالكامل **في كل مرة**، فتظهر الشاشة فارغة ولا يظهر أي مُسجَّل — قديمًا كان أو جديدًا — في أي قائمة (الكل/المعلقون/المعتمدون/المرفوضون). الاختبارات الحالية تُحاكي عميل Supabase بالكامل ولا تُجرب الاستعلام الحقيقي، لذلك لم يُكتشف.
2. **سبب ثانوي مستقل** يخفي أزرار الموافقة حتى بعد إصلاح الاستعلام: اشتقاق صلاحية الاعتماد `actorCanApprove` يعتمد على وجود صف المُعتمد نفسه **ضمن القائمة المُرشَّحة حاليًا**، فيختفي الزر عند فتح تبويب «المعلقون» مباشرة (تحميل بارد) أو عند فشل الكاش.
3. **فجوة تفاعلية كاملة في «منحه الصلاحيات المناسبة لدوره»:** الموافقة الحالية تُمنح معها صلاحية `viewer` مثبتة في الخادم فقط، ولا توجد **أي شاشة** تستدعي `admin_set_user_roles` لتغيير دور المستخدم بعد الاعتماد. أي أن «منح الدور المناسب» غير ممكن اليوم إطلاقًا من الواجهة.
4. **رسائل التسجيل:** النص الحالي عام واحد يحتوي شرطًا داخله («إذا كنت المالك الأول… وإلا…»). المطلوب: تنبيه **«أنت المالك الأول»** للمُسجِّل الأول فقط، و**«تم التسجيل بنجاح وفي انتظار موافقة الإدارة»** لمن بعده. التمييز ممكن بشكل موثوق من جهة العميل (تفصيل §3).
5. **تم استبعاد سياسات RLS كسبب** — المالك المعتمد يرى صفوف `pending` قانونيًا (تفصيل §2.4).

## 1. المسار الحالي كما هو منفَّذ

```
┌─ التسجيل (Login.tsx → AuthContext.signUp → supabase.auth.signUp)
│    BEFORE INSERT  auth.users → confirm_first_auth_user_email()
│       • أول تسجيل فقط: يُغلق مطالبة first_admin_bootstrap_state ويؤكد البريد فورًا
│    AFTER INSERT   auth.users → handle_new_user()
│       • أول مستخدم: profile + دور owner (بكل الصلاحيات) + approval_status='approved'
│       • كل من بعده: profile فقط + approval_status='pending' + بلا أي دور
│
├─ الرسالة بعد التسجيل: نص عام واحد signup.confirmation (يحتوي شرطًا داخله)
│
└─ الاعتماد (المالك/المدير):
     /settings/system/users → useUsersManagement.fetchUsers()
       select ..., user_roles(roles(...)) from profiles   ← ✗ دمج غامض (PGRST201)
     أزرار موافقة/رفض تظهر إذا actorCanApprove             ← ✗ اشتقاق هش (§2.2)
     approve-user Edge Function → admin_approve_user(p_user_id,'approve',p_executor_id)
       • يعتمد الحساب + يؤكد البريد + يمنح viewer مثبتًا    ← ✗ بلا اختيار دور (§2.3)
```

السياسات والمشغّلات (من `20261017000000` و`20261017010000`) سليمة في تصميمها: التسجيل لاحق يُنشئ صف `pending` بلا دور، والاعتماد حصري للمالك/`super_admin` عبر Proxy خدمة يتحقق من هوية المنفّذ. **العطل في طبقة القراءة/التفاعل، لا في طبقة الأمان.**

## 2. النتائج — المشكلة الأولى: عدم الظهور في قائمة الاعتمادات

### 2.1 السبب الجذري: دمج PostgREST غامض (PGRST201) — ثقة عالية

**الحقائق المثبتة من المخطط (مصدرها الهجرات):**

```sql
-- 20260930000000_init_core_schema.sql:126-131
create table public.user_roles (
  user_id    uuid not null references public.profiles (id) on delete cascade,   -- FK #1
  role_id    uuid not null references public.roles (id) on delete cascade,
  granted_by uuid references public.profiles (id) on delete set null,           -- FK #2 ← أيضًا إلى profiles
  ...
);
```

**الاستعلام المصاب** (`src/hooks/useUsersManagement.ts:132-135`):

```
id, email, full_name, status, approval_status, created_at, updated_at,
user_roles(roles(slug, name_ar, name_en, is_super_admin))
```

دمج `user_roles` من `profiles` **بلا توضيح أي المفتاحين** — والمستندان بينهما `user_roles.user_id` و`user_roles.granted_by`. حسب توثيق PostgREST الرسمي (v12 — قسم _Foreign Key Joins on Multiple Foreign Key Relationships_)، وعندما يكون بين جدولين أكثر من مفتاح أجنبي واحد يرفض التخمين ويردّ:

```json
HTTP/1.1 300 Multiple Choices
{
  "code": "PGRST201",
  "message": "Could not embed because more than one relationship was found for 'profiles' and 'user_roles'",
  "hint": "Try changing 'user_roles' to one of the following: 'user_roles!user_id', 'user_roles!granted_by'. ..."
}
```

نفس السلوك مؤكد على Supabase المُستضاف (مناقشة supabase#22870 — نفس زوج الجداول `profiles`/`user_roles` حرفيًا)، وأعطاله موثّقة في مشاريع حقيقية بنفس الأعراض: «كان يفشل بصمت في كل مكان… الصفحات تظهر فارغة رغم أن الإدخالات كانت تنجح» (cookzer#67).

**ماذا يحدث في الشاشة اليوم:** `fetchUsers` يلتقط الخطأ فيُطبَّقه `mapPostgrestError` إلى `unknown` (لأن `PGRST201` لا يطابق أي فرع)، وتُعرض حالة الخطأ `users.error.unknown` مع **صفر صفوف** → من وجهة نظر المستخدم: «المُسجَّل الجديد لا يظهر ضمن قائمة الاعتمادات».

**لماذا لم يُكتشف:**

- اختبارات `useUsersManagement.test.tsx` تُحاكي `getSupabase()` بالكامل ولا تُطلق الاستعلام الحقيقي أبدًا.
- تدقيق القاعدة (`scripts/audit/database.mjs`) يتصل بـ PostgreSQL مباشرة (SQL)، أي يتجاوز PostgREST وطبقة الدمج نهائيًا.
- تدقيق العيش 2026-10-01 لم يختبر أي استعلام PostgREST بدمج.

**النطاق الكامل للإصابة:** نفس النمط موجود في شاشة الدعم (`useSupportManagement.ts` — `TICKET_COLUMNS`/`REPLY_COLUMNS` تدمج `user_roles` داخل `profiles`)، أي أن قوائم التذاكر ستنهار بالخطأ نفسه. (دمج `profiles` من `tickets` نفسه سليم لأن `tickets.assigned_to` يشير إلى `auth.users` لا إلى `profiles`.)

**الإصلاح المصغّر (بلا تغيير في شكل الاستجابة):**

```diff
- user_roles(roles(slug, name_ar, name_en, is_super_admin))
+ user_roles!user_id(roles(slug, name_ar, name_en, is_super_admin))
```

تلميح `!user_id` يحدّد المفتاح الأجنبي المقصود، واسم الحقل في الاستجابة يبقى `user_roles` كما هو → طبقة التحليل `parseUserRow` لا تتغير.

### 2.2 سبب ثانوي مستقل: أزرار الموافقة تختفي في تبويب «المعلقون»

`actorCanApprove` (`useUsersManagement.ts`) يُشتق من وجود **صف المُعتمد نفسه** ضمن:

```ts
[...users, ...(queryClient.getQueryData(USERS_QUERY_KEY) ?? [])];
```

- `users` هو القائمة **بعد الفلترة** — وصف المُعتمد (مالك) `approval_status='approved'`، فهو غير موجود إطلاقًا في فلتر `pending`.
- الكاش الاحتياطي `USERS_QUERY_KEY` («الكل») يفشل عند التحميل البارد مباشرة على تبويب «المعلقون» أو بعد انتهاء صلاحية الكاش.

النتيجة: `canApprove=false` → أزرار **موافقة/رفض لا تُعرض** رغم ظهور الصف. يجب أن يأتي هذا القرار من مصدر ثابت لا يتأثر بالفلتر (استعلام مخصص لدور المُعتمد، أو قناة القدرات)، مع مواءمة معياره مع الخادم (`owner`/`super_admin` في `admin_approve_user`).

### 2.3 فجوة «منحه الصلاحيات المناسبة لدوره»

- `admin_approve_user` يمنح **`viewer` فقط** (مثبت في SQL)، ولا يقبل دورًا آخر.
- لا توجد **أي** واجهة تستدعي `admin_set_user_roles` (الـ RPC المحمي لتغيير أدوار مستخدم موجود في القاعدة منذ `20261001130000`) — شاشة الأدوار تعدّل مصفوفة `role→permission` وعدد المُسنَدين فقط.

أي أن المطلوب في البلاغ («الموافقة على إدراجه **ومنحه الصلاحيات المناسبة لدوره**») يحتاج مسارًا جديدًا: اختيار الدور **لحظة الاعتماد** (مقترح في §4.3)، أو على الأقل شاشة لتعديل أدوار المستخدمين بعد الاعتماد.

### 2.4 ما تم استبعاده: RLS ليست السبب

للمالك (`is_admin()` = يحمل `*`، و`approval_status='approved'`):

| الطبقة             | السياسة                                                           | النتيجة للمالك    |
| ------------------ | ----------------------------------------------------------------- | ----------------- |
| Permissive SELECT  | `"Users read their own profile"`: `auth.uid() = id or is_admin()` | يرى **كل** الصفوف |
| Restrictive SELECT | `approved_users_only`: `id = auth.uid() or is_approved_user()`    | يمرّ (معتمد)      |

صفوف `pending` ظاهرة قانونيًا للمالك — العطل في الاستعلام نفسه (§2.1) لا في الرؤية. (المعايير في `scripts/audit/database.mjs` تؤكد أن المستخدم `pending` نفسه يرى صفه فقط — وهو سلوك مقصود.)

## 3. النتائج — المشكلة الثانية: رسائل نموذج التسجيل

**الحالة اليوم:** `signup.confirmation` نص عام واحد:

> «تم إنشاء الحساب. إذا كنت المالك الأول، سجّل دخولك الآن؛ وإلا انتظر موافقة الإدارة.»

**المطلوب:**

| الحالة                     | التنبيه                                          |
| -------------------------- | ------------------------------------------------ |
| أول مُسجِّل (المالك الأول) | **«أنت المالك الأول»** (تنبيه مميّز)             |
| كل من بعده                 | **«تم التسجيل بنجاح وفي انتظار موافقة الإدارة»** |

**كيف يميّز الواجهة الحالتين بموثوقية (بلا استعلام إضافي للخادم):**

1. `confirm_first_auth_user_email` يؤكد بريد **المالك الأول فقط** داخل نفس معاملة الإدراج، لذلك يردّ `supabase.auth.signUp` بحالتين واضحتين:
   - **جلسة فورية** أو `user.email_confirmed_at` مُعيَّن ⟵ المالك الأول (حسابه معتمد فورًا).
   - بلا جلسة وبريد غير مؤكد ⟵ مُسجَّل عادي (`pending`) — يستحيل أن يكون المالك الأول.
2. **التحقق الإضافي للحافة** (مشروع بتأكيد بريد مُعطَّل يردّ بجلسة للجميع): قبل `signOut` اللحظي في `signUp`، تُقرأ `approval_status` من صفّي الشخص (RLS يسمح للمستخدم برؤية صفه حتى وهو `pending` — مقصودًا بهذا الشكل في الهجرة). `approved` ⟵ «أنت المالك الأول»، `pending` ⟵ «في انتظار موافقة الإدارة».

**ملفات التنفيذ:** `AuthContext.signUp` (يعيد `outcome: 'first-owner' | 'pending-approval'` بدل `requiresEmailConfirmation` أو إضافةً إليه)، `Login.tsx` (نمط عرضين منفصلين للتنبيه)، `ar.ts`/`en.ts` (مفتاحان جديدان بالنص المطلوب حرفيًا).

## 4. خطة الإصلاح المقترحة (بعد الموافقة)

### 4.1 إصلاح PGRST201 (الأولوية القصوى — مستقل وآمن)

| الملف                               | التغيير                                                                                                                  |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `src/hooks/useUsersManagement.ts`   | `user_roles!user_id(roles(...))` داخل `PROFILE_COLUMNS`                                                                  |
| `src/hooks/useSupportManagement.ts` | نفس التصحيح في `TICKET_COLUMNS` و`REPLY_COLUMNS`                                                                         |
| اختبارات                            | اختبار تراجعي يثبّت أن نصوص `SELECT` تحتوي التلميح المُوضَّح (لا يمكن التراجع عنه بصمت) + اختبارات `parseUserRow` كما هي |

لا حاجة لأي هجرة قاعدة بيانات. يُنشر وحده إن رُغب.

### 4.2 تثبيت اشتقاق صلاحية الاعتماد

- مصدر مستقل عن الفلتر: استعلام مخصص صغير لأدوار المُعتمد (`user_roles?select=roles(slug,is_super_admin)&eq=user_id=…`) أو قناة `useAuthCapabilities`، مع إبقاء معيار الخادم (`owner`/`super_admin`) مطابقًا في الواجهة.
- (خيار أوسع — قرار §5.2): توسيع بوابة الخادم إلى `users.manage` كما في TODO داخل `UsersManagement.tsx`.

### 4.3 الموافقة مع اختيار الدور («منحه الصلاحيات المناسبة لدوره»)

1. **القاعدة** — تعديل `admin_approve_user` لبارامتر اختياري `p_role_slug` (الافتراضي `viewer` للتوافق):
   - التحقق: الدور موجود، و`is_super_admin = false`، و`slug <> 'owner'` (الأدوار المحمية غير قابلة للمنح — كما في `admin_set_user_roles`).
   - المنح داخل نفس المعاملة (تحت نفس أقفال التزامن) + تدوين الدور في `metadata` سجل التدقيق.
   - **مهم:** استبدال الدوال الحالية يتطلب `DROP` للنسخ القديمة (3-argument ثم 2-argument) وإعادة إنشائها؛ لأن ترك النسخة القديمة (3-argument) مع نسخة (4-argument لها default) يُنشئ غموضًا في الاستدعاء (`function is not unique`). الهجرة الجديدة تُعيد بناء السلسلة كاملة: النواة 4-argument + اللفافة 2-argument كما هي.
2. **Edge Function `approve-user`** — قبول `roleSlug` اختياري والتحقق من صيغته وتمريره.
3. **الواجهة** — زر «موافقة» يفتح حوارًا بسيطًا فيه قائمة أدوار غير محمية (`viewer` / `editor` / `admin` + أي دور مخصص) + زر رفض كما هو. رسالة النجاح تصبح «تمت الموافقة على {name} بدور {role}» بدل «تم تحديث حالة».

### 4.4 رسائل التسجيل

- مفتاحان جديدان بالعربية (وبالإنجليزية مقابلة):
  - `signup.firstOwner`: **«أنت المالك الأول»** — «تم تفعيل حسابك ومنحك كل الصلاحيات. يمكنك تسجيل الدخول الآن.»
  - `signup.pendingApproval`: **«تم التسجيل بنجاح وفي انتظار موافقة الإدارة»**
- التمييز حسب §3، مع اختبارات Login للحالتين.

### 4.5 إصلاحات طفيفة في نفس النطاق

- رسالة نجاح الاعتماد/الرفض تحل محل `users.success.statusUpdated` العام.
- (اختياري) عدّاد «طلبات معلقة» على عنصر القائمة الجانبية — خارج النطاق ما لم يُطلب.

### 4.6 خطة التحقق

1. **قبل التنفيذ (تشخيص حي — دقيقة واحدة)** على المشروع المربوط:

```bash
curl -s -i "https://<PROJECT-REF>.supabase.co/rest/v1/profiles?select=id,approval_status,user_roles(roles(slug))&limit=1" \
  -H "apikey: <ANON-KEY>" -H "Authorization: Bearer <JWT-لمستخدم مسجل>"
# المتوقع اليوم:  HTTP/1.1 300 + {"code":"PGRST201", ...}   ← يؤكد §2.1
# بعد الإصلاح (select=user_roles!user_id(...)):              HTTP 200 + البيانات
```

2. اختبارات وحدة (vitest): نصوص SELECT المُصححة، `actorCanApprove` لا يتأثر بالفلتر، رسائل التسجيل للحالتين، حوار الاعتماد يرسل `roleSlug`.
3. تدقيق قاعدة (`scripts/audit/database.mjs`): حالة `admin_approve_user` بالدور المختار + رفض الأدوار المحمية + إعادة التشغيل الآمنة للهجرة.
4. E2E يدوي: تسجيل مستخدم → ظهوره في «المعلقون» → اعتماده بدور `editor` → دخوله بدوره → ثم اختبار الرفض.

## 5. قرارات مطلوبة من المالك قبل التنفيذ

1. **منح الدور عند الاعتماد (مقترح §4.3)** أم الاكتفاء بإصلاح الظهور + إضافة شاشة منفصلة لتغيير الأدوار لاحقًا؟ _(التوصية: الخيار الأول — يحقق صياغة البلاغ حرفيًا.)_
2. **بوابة الاعتماد في الواجهة/الخادم:** إبقاء المالك+`super_admin` فقط، أم توسيعها إلى حامل `users.manage` (يتطلب تعديل `admin_approve_user` + مواءمة الواجهة)؟ _(التوصية: الإبقاء كما هي الآن لتقليل النطاق.)_
3. **صياغة التنبيهين** حرفيًا كما في §4.4؟
4. **ترتيب النشر:** (أ) إصلاح PGRST201 وحده أولًا كإصدار مستقل، أم (ب) حزمة واحدة (المشكلة 1 + 2 + الرسائل)؟ _(التوصية: أ ثم ب — الأول يعيد الحياة للشاشة فورًا.)_
