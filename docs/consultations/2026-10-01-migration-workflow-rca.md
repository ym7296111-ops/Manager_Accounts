## 0. الخلاصة التنفيذية — وتصحيح مقدّمتين في طلب الدراسة

الفحص المبني على الواقع الفعلي للمستودع وتشغيلات GitHub Actions **ينفي الفرضية الواردة في الطلب** في نقطتين
جوهريتين. يجب تصحيحهما قبل أي ترقيع، لأن الترقيع المبنى عليهما سيعالج عطلاً غير موجود:

| المقدّمة في الطلب                                                            | الحكم       | الدليل                                                                                                                                                           |
| ---------------------------------------------------------------------------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| السبب هو تعارض سجل الترحيلات `Remote migration versions not found in local…` | ❌ **خاطئ** | الخطوة الفاشلة حالياً هي `Lint schema` داخل وظيفة `test_and_lint`، **وليست** `Push migrations`                                                                   |
| الدمج الأخير أحدث فجوة تاريخية بسبب حذف/إعادة تسمية ملف                      | ❌ **خاطئ** | `git log --all --name-status` على `supabase/migrations/` يُظهر رمز الحالة `A` فقط (9 إضافات)، **صفر** `R`/`D`/`M` منذ بداية المستودع                             |
| قاعدة البيانات معلّقة لأن `db push` فشل في التطبيق                           | ⚠️ **جزئي** | في التشغيلات الفاشلة الثمانية الأخيرة **لم تبدأ** `deploy_production` إطلاقاً (`in 0s`) بسبب `needs: test_and_lint` ⇒ لم يصل أي DDL إلى الإنتاج من هذه التشغيلات |

**السبب الجذري الحقيقي (مثبَت بالتشغيل الفعلي):** عيب برمجي في دالة `public.admin_update_app_identity()`
داخل الترحيل `20261001150000_app_identity_schema.sql`. الدالة **تفشل عند تنفيذها** برسالة:

```
malformed array literal: "name_ar"
```

وتمرّ على `supabase db reset` بلا أي خطأ (لأن PL/pgSQL **لا يتحقق من أجسام الدوال عند `CREATE FUNCTION`**)،
بينما `supabase db lint` في CLI المُثبَّت (`2.118.0`) يشغّل إضافة **`plpgsql_check`** التي تفحص الأجسام
ساكناً — فتُظهر الخطأ وتُرجع `exit code 1`.

### 1.2 هل يوجد ملف قديم محذوف أو مُعاد تسميته أحدث فجوة؟

**لا — وهذا مُثبَت وليس استنتاجاً:**

```bash
git log --all --name-status --format= -- supabase/migrations/ | cut -f1 | sort -u
# الناتج: A        (أي: إضافات فقط)
```

- عدد الملفات على `main`: **9**، وعدد الإصدارات التي وُجدت يوماً في أي مرجع: **9** ⇒ المجموعتان متطابقتان.
- كل الـ 11 PR في المستودع حالتها `MERGED`، ولا يوجد فرع يتيم يحمل إصدار ترحيل غير مدموج
  (`git ls-remote --heads origin` → 11 فرعاً مقابل 11 PR مدموجاً).

**النتيجة:** لا توجد فجوة تاريخية محلية، ولا يوجد أي مبرر تقني لرسالة
`Remote migration versions not found in local migrations directory` صادرة عن **حالة المستودع الحالية**.
إن كانت تلك الرسالة قد ظهرت فعلاً، فسببها الوحيد الممكن هو وجود صفوف في جدول الإنتاج
أُدخلت من خارج مسار الملفات (SQL Editor يدوي، أو ترحيل شُبّه ثم لم يُلتزم) — وهذا **افتراض يحتاج تحققاً
من الإنتاج مباشرة** (انظر §1.3)، وليس نتيجة للدمج الأخير.

### 2.1 السلسلة السببية الحقيقية للفشل (من تشغيلات فعلية)

**قراءتان حاسمتان:**

1. **بوابة `Lint schema` هي الحاجز الحالي، وهي سابقة زمنياً ومنطقياً لأي حديث عن سجل الترحيلات.**
   `deploy_production` معلَّقة بـ `needs: test_and_lint`، فلم تُنفَّذ خطوة `Link project` ولا `Push migrations`
   في أيٍّ من التشغيلات الثمانية الأخيرة ⇒ **لم يُطبَّق أي DDL على الإنتاج منها**.
2. **أربعة من تشغيلات `workflow_dispatch` الستة الأخيرة أُطلقت على الفرع لا على `main`**، وشرط الوظيفة

   أي أن إعادة التشغيل اليدوية كانت **محكومة بالفشل المُسبق** — وهذا بالضبط «إعادة التشغيل العشوائية»
   التي طلبتم تجنّبها.

### 2.2 الدليل على أن العيب «جسم دالة» وليس «مخطط قاعدة بيانات»

تشغيل الـ linter الرسمي (`splinter`) على المخطط الكامل بعد الترحيلات التسعة:

```

RESULT: lint gate passes
```

مستويات القواعد ثابتة عبر كل إصدارات الـ linter (`2026.07.0`، `2026.08.0`، `2026.09.0`، `2026.09.1`، `main`)،
والقواعد الثمانية ذات المستوى `ERROR` كلها **لا تنطبق** على هذا المخطط:

| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `rls_disabled_in_public`                       | `public.app_identity_settings` مُفعَّل عليها RLS (سطر 80) و`force` (سطر 81)                               |
| `policy_exists_rls_disabled`                   | نفس السبب؛ والقاعدة تستثني `storage` أصلاً                                                                |

إذن البوابة التي أحمرّت ليست فاحص المخطط، بل الطبقة الأخرى. وتوثيق CLI `v2.118.0` الرسمي
(`apps/cli/docs/supabase/db/lint.md`) ينصّ حرفياً:

> Runs the **`plpgsql_check`** extension against the local database … The default lint level is `warning` …
> The `--fail-on` flag … `error`: Exit with a non-zero status code **only if errors are found**.

### 2.3 العيب نفسه — مُعاد إنتاجه بالتشغيل لا بالاستنتاج

السطور الستة في `20261001150000_app_identity_schema.sql`:

```sql
180:  v_changed text[] := array[]::text[];
...
322:    v_changed := v_changed || 'name_ar';
325:    v_changed := v_changed || 'name_en';
328:    v_changed := v_changed || 'admin_email';
331:    v_changed := v_changed || 'phone';
334:    v_changed := v_changed || 'logo_path';
337:    v_changed := v_changed || 'favicon_path';
```

`text[] || 'literal'` يحلّه PostgreSQL إلى **`anyarray || anyarray`** (وليس `anyarray || anyelement`)،
فيحاول قراءة `'name_ar'` كلiteral مصفوفة ⇒ `malformed array literal`.

**القياس الفعلي** (PGlite + مثبّت المستودع + الترحيلات التسعة + مستخدم `super_admin`):

| الحالة                       | نتيجة الـ RPC                           | صفوف `audit_logs` لكيان `app_identity_settings` | الحالة المُخزَّنة                              |
| ---------------------------- | --------------------------------------- | ----------------------------------------------- | ---------------------------------------------- |
| الكود كما هو مدموج في `main` | ❌ `malformed array literal: "name_ar"` | **0**                                           | `name_ar='نظام الإدارة'`, `assets_revision=1`  |
| بعد الإصلاح المقترح          | ✅ نجاح                                 | **1** (`settings.updated`)                      | `name_ar='نظام الاختبار'`, `assets_revision=2` |

**ثلاث نتائج تشغيلية بالغة الأهمية:**

- مسار الكتابة الوحيد للشاشة الخامسة **معطَّل كلياً**: لا تعديل اسم، لا تواصل، لا شعار، لا أيقونة.
- **`db reset` يمرّ بنجاح رغم ذلك** ⇒ البوابة الوحيدة التي تكشفه هي `db lint` (أو استدعاء الدالة).
  هذه هي الثغرة المنهجية التي سمحت بمرور PR #11 من كل الفحوص الأخرى.
- **`audit_logs` سليم بنيوياً ولم يتلوّث**: الفشل يحدث **قبل** عبارة `insert into public.audit_logs`،
  والـ RPC يعمل ضمن معاملة واحدة ⇒ لا سجلات نصفية ولا أثر جانبي. الجدول سليم، لكنه **ناقص** صفوفاً
  لكل محاولة تحديث فاشلة.

### 2.4 لماذا تُبقي خيارات `workflow_dispatch` القاعدة معلّقة؟

```yaml
workflow_dispatch:
  inputs:
    dry_run: { type: boolean, default: true } # ← الافتراضي true
    include_all: { type: boolean, default: false }
    mark_applied: { type: string, default: '' }
```

```yaml
- name: Repair migration history
  if: ${{ github.event_name == 'workflow_dispatch' && inputs.mark_applied != '' }}
  run: supabase migration repair --linked --status applied "${versions[@]}" --yes

- name: Push migrations
  env:
    DRY_RUN: ${{ github.event_name == 'workflow_dispatch' && inputs.dry_run }}
```

| الظاهرة                                                    | التفسير الميكانيكي الدقيق                                                                                                                                                                                                                                                |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| الضغط على «Run workflow» بالقيم الافتراضية لا يُطبّق شيئاً | `dry_run` افتراضياً `true` ⇒ يُضاف `--dry-run` ⇒ الـ CLI **يقرأ** الفرق ويطبعه ثم يخرج بلا أي DDL. هذا تصميم مقصود للأمان، لكنه يجعل «إعادة التشغيل» تبدو كأنها تعمل وهي لا تفعل شيئاً.                                                                                  |
| `history repair` وحده يترك القاعدة معلّقة                  | `supabase migration repair --status applied` **يكتب صفاً في `schema_migrations` فقط ولا يُنفّذ حرف SQL واحداً**. وبما أن `dry_run` يبقى `true` في نفس التشغيل، فإن خطوة `Push migrations` التالية تعمل بصيغة `--dry-run` ⇒ النتيجة الصافية: سجل مُعدَّل، مخطط بلا تغيير. |
| الإصلاح يحتاج نقرتين متتاليتين لا واحدة                    | التشغيل الأول (`mark_applied=…`) يُصلح السجل، ثم **يجب** تشغيل ثانٍ بـ `dry_run=false` للتطبيق. لا يوجد أي ترابط يفرض الثانية، ولا تحذير يقول إن الأولى وحدها غير كافية.                                                                                                 |
| الإطلاق من الفرع لا يُطبّق أبداً                           | `if: github.ref == 'refs/heads/main'` ⇒ **4 من تشغيلات `workflow_dispatch` الفاشلة الستة** (`36908329266`, `36909236874`, `36909625271`, `36910140490`) كانت على الفرع `arena/01a0f858-admin-system` ومحكومة بالتخطّي بنيوياً.                                           |
| `include_all` مغلق افتراضياً                               | عند وجود إصدارات محلية سبقت إصدارات مُسجَّلة بعيداً، يرفض الـ CLI الدفع بلا `--include-all` ⇒ فشل إضافي صامت السبب.                                                                                                                                                      |

### 2.5 هندسة المزامنة الذاتية (Self-Healing) المطلوبة

المبدأ: **اجعل الفرق حالةً مُعلَنة قابلة للقرار، لا استثناءً بشرياً.** ثلاث طبقات:

**الطبقة أ — خطوة `Reconcile migration history` (قراءة أولاً، ثم قرار محسوب)**

تُنفَّذ بعد `Link project` وقبل `Push migrations`، وتنتج مصفوفة تصنيف لا تخمين:

```
local_versions    = أسماء الملفات (^\d{14}) مرتّبة
remote_versions   = select version from supabase_migrations.schema_migrations
pending           = local − remote          → تُطبَّق بـ db push
orphan_remote     = remote − local          → تنبيه ::error + إيقاف (لا إصلاح تلقائي)
out_of_order      = pending فيها إصدار < max(remote) → يتطلب include_all=true صراحةً
```

**الطبقة ب — إصلاح ذاتي مُقيَّد بقاعدة أمان واحدة**

| الحالة                      | الإجراء التلقائي                                               | لماذا ليس أكثر من ذلك                                                             |
| --------------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `pending` غير فارغة ومرتّبة | `supabase db push --linked --yes`                              | آمن، وهذا هو المسار الطبيعي                                                       |
| `out_of_order`              | `--include-all` **فقط** إذا كان مدخل `allow_out_of_order=true` | الدفع خارج الترتيب قرار هندسي، لا يجب أن يُتَّخذ ضمناً                            |
| `orphan_remote`             | **توقّف + تنبيه**؛ لا `repair --status removed` تلقائياً       | حذف صف من سجل الإنتاج قد يُخفي مخططاً مطبَّقاً فعلاً — أخطر قرار في المنظومة كلها |
| إصدار مُسجَّل ولم يُنفَّذ   | `repair --status applied` **فقط** بمدخل صريح + طباعة الـ diff  | لأنه يكتب في السجل دون تنفيذ SQL؛ يجب أن يكون مُسجَّلاً باسم من قرّره             |

**الطبقة ج — إغلاق الثغرة التي سمحت بمرور هذا العيب أصلاً**

بوابة `Lint schema` وحدها لا تكفي (فهي مرتبطة بإصدار CLI). تُضاف خطوة مستقلة لا تعتمد على الـ CLI:

```
- name: Smoke-test every SECURITY DEFINER RPC
  run: |
    # يستدعي كل RPC إداري بمُدخلات حدية داخل قاعدة مؤقتة، ويتوقع إما نجاحاً
    # أو خطأً مقصوداً (errcode معروف) — لا «malformed array literal» ولا «undefined column».
```

هذه الخطوة كانت ستكشف عيب PR #11 **حتى لو تعطّل `db lint` بالكامل**، لأنها تُنفّذ الأجسام فعلاً.

### 3.4 ضمان عدم التكرار عند الشاشة السادسة والسابعة

| الضابط                                                                                                                                        | ماذا يمنع بالضبط                                                                                  |
