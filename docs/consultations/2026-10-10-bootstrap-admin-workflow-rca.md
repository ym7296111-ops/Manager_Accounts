## 0. الخلاصة

الـ Workflow **يصل إلى خطوة تشغيل السكريبت ثم يخرج فورًا** (أقل من ثانية بعد `npm ci`). تعريف YAML سليم: حدث يدوي فقط، بيئة `Production`، مهلة 10 دقائق، والأسرار تُمرَّر بالأسماء الصحيحة. الفشل ليس في `npm ci` ولا في تخطي الوظيفة (`github.ref == refs/heads/main` تحقق لأن التشغيل كان على `main`).

لم يمكن تنزيل نص السجل الكامل من هذه البيئة (مستقبل السجلات على Azure Blob غير مسموح)، لذلك السبب الدقيق داخل السكريبت **غير مثبت من الـ log**. الكود نفسه يخفي السبب في مسارين:

1. معالج `WHEN OTHERS` في `bootstrap_first_super_admin` كان يحوّل كل رفض SQL إلى `Bootstrap refused: Internal processing error.`
2. `scripts/bootstrap-admin.ts` كان يطبع رمز الخطأ فقط (`P0001` / `HTTP_422`) ويتجاهل `error.message`.

أي تشغيل لاحق على الحساب نفسه يفشل عمدًا: المسار الآلي **لا يعيد استخدام** حساب Auth قائم. إذا أنشأ التشغيل الأول المستخدم ثم فشل المنح، التشغيل الثاني يرفض قبل المنح.

## 1. ما الذي فُحص في الـ Workflow

| السؤال                              | النتيجة                                                                                                                                           |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| هل يستمع لـ `workflow_dispatch`؟    | نعم. **لا** يستمع لـ `push` إلى `main` — وهذا متعمد (تهيئة لمرة واحدة، ليست عند كل دمج).                                                          |
| هل بيئة `Production` محددة؟         | نعم، `environment.name: Production`. لا توجد قواعد حماية (لا required reviewers).                                                                 |
| هل الأسرار تُمرَّر؟                 | نعم عبر متغير البريد وكلمة المرور الأوليين وبيانات Supabase. إذا كانت القيم **Variables** بدل **Secrets** فبعضها يصل فارغًا ويفشل السكريبت فورًا. |
| هل `npm ci` ينجح؟                   | نعم في التشغيلين.                                                                                                                                 |
| هل المهلة مناسبة؟                   | `timeout-minutes: 10`. الفشل لم يكن مهلة.                                                                                                         |
| هل تُلتقط الأخطاء بوضوح في Actions؟ | لا. التعليق الوحيد كان `Process completed with exit code 1`. لا يوجد `::error::` من السكريبت.                                                     |

اسم الـ RPC في الكود هو `bootstrap_first_super_admin` وليس `automated_super_admin_bootstrap` (هذا اسم ملف الترحيل فقط).

## 2. ما الذي فُحص في السكريبت

| الفحص                                           | قبل الإصلاح                                                                             |
| ----------------------------------------------- | --------------------------------------------------------------------------------------- |
| قراءة بيانات Supabase واعتماد الحساب الأولي     | نعم من `process.env`، مع `trim` ما عدا كلمة المرور.                                     |
| عميل Supabase                                   | `createClient(url, key, { auth: { persistSession: false, autoRefreshToken: false } })`. |
| التحقق من الاتصال قبل الإنشاء                   | **لا** — أول طلب شبكة كان `auth.admin.createUser`.                                      |
| `auth.admin.createUser` + `email_confirm: true` | نعم.                                                                                    |
| المستخدم الموجود مسبقًا                         | يُرفض ولا يُرفع. لا رسالة تشرح حذف اليتيم.                                              |
| استدعاء RPC                                     | `bootstrap_first_super_admin({ p_target_email })`.                                      |
| نجاح المنح                                      | يشترط `status === 'success'` ورسالة ثابتة. jsonb كنص كان سيفشل بعد منح ناجح.            |
| `console.error`                                 | نعم، لكن بدون رسالة PostgREST/Auth.                                                     |

اختبار محلي بدون أسرار (بعد `npm ci`):

```
[bootstrap-admin] Required bootstrap email variable is missing.
[bootstrap-admin] Bootstrap password must be at least 12 characters long.
[bootstrap-admin] SUPABASE_URL must be a valid project URL.
```

لا يمكن استدعاء مشروع `*.supabase.co` من هذه البيئة (قائمة المضيفين المسموحة لا تتضمنه)، ولا قراءة قيم أسرار GitHub (403).

## 3. أسباب مرشحة حسب التوقيت (~0–1 ث)

مرتبة من الأكثر إلى الأقل ملاءمة للأدلة المتاحة:

1. **أسرار فارغة أو في المكان الخطأ** (Environment Variables بدل Secrets، أو بيئة Preview). يفشل السكريبت قبل أي شبكة.
2. **`createUser` فشل** (مفتاح anon بدل service_role، كلمة مرور مرفوضة، أو الحساب موجود من التشغيل الأول).
3. **RPC فشل بعد إنشاء المستخدم** (مخطط PostgREST غير محدَّث بعد `db reset --linked` → `PGRST202`، أو رفض SQL مغلّف كـ `P0001`). يترك حساب Auth يتيمًا فيمنع إعادة التشغيل.
4. **`FORCE RLS` على `user_roles` بلا سياسة كتابة للمالك** — على الاستضافة `postgres` ليس superuser؛ إن لم يملك `BYPASSRLS` فإن `INSERT` داخل الـ RPC يفشل. محليًا `postgres` superuser لذلك اختبار CI كان ينجح.

## 4. الإصلاحات في هذا الفرع

- فحص وجود الأسرار الأربعة قبل التشغيل، مع `::error::` يلخص `[bootstrap-admin]`.
- استطلاع Auth admin ثم استدعاء RPC بهوية preflight **قبل** `createUser` حتى لا يُترك يتيم عند `PGRST202`.
- تمرير رسائل Auth/PostgREST بعد تنقيتها، وشرح استرداد الحساب الموجود.
- إعادة رفع رسائل `Bootstrap refused:` من SQL بدل تغليفها كلها.
- سياسة كتابة للمالك على `user_roles` تحت FORCE RLS (`20261010140000_...`).
- `npm run bootstrap:admin` للاختبار المحلي بعد تصدير المتغيرات.

## 5. ترتيب إعادة التشغيل على الإنتاج

1. دمج هذا الفرع إلى `main`.
2. تشغيل **Supabase Migrations** على `main` لتطبيق `20261010140000`.
3. في لوحة Auth: إن وُجد الحساب الأولي بلا دور `super_admin`، احذفه.
4. تأكيد بيانات اعتماد التدفق القديم في **Production → Environment secrets**.
5. تشغيل **Bootstrap First Super Admin** من `main` مرة واحدة.
6. بعد الدخول الناجح غيّر كلمة المرور واحذف بيانات الاعتماد الأولية القديمة من البيئة.
