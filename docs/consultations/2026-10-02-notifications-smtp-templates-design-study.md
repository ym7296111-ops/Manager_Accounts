# دراسة استشارية معمارية — شاشة التنبيهات وقوالب الرسائل الديناميكية (Notifications & Message Templates)

> **الحالة:** مسودة استشارة للنقاش والاعتماد — **لا كود تنفيذي ولا ملفات ترحيل SQL** في هذه المرحلة.
> كل ما ورد أدناه **تصريحي** (جداول حقول · عقود دوال · مخططات منطقية · مصفوفات سياسات) ومقصوده تثبيت المفاهيم والقرارات لا الكتابة. الكود والترحيل يأتيان في «المرحلة الثانية» بعد اعتماد بوابة القرارات (§6).
> **البيئة:** Vite 8 + React 19 + TypeScript 6 (strict) + Tailwind CSS 4 + TanStack Query v5 + Supabase (PostgreSQL / RLS / Storage / Realtime / Edge Functions).
> **الشاشة:** السابعة والأخيرة من سبع شاشات ضبط — المسار `/settings/app/notifications` — ما زالت تعرض `EmptyState` في `SettingsPage`، ووصفها المنتجّي في القاموس: «تفعيل قنوات التنبيه وقواعد الإرسال».
> **المبدأ الحاكم:** المشروع **قالب قابل لإعادة الإنتاج**. لذلك: (أ) صفر ارتكاز على مزود بريد بعينه في الكود أو في قاعدة البيانات، (ب) صفر أسرار نصية في أي مكان يقرأه العميل، (ج) كل شيء قابل للتهيئة من الشاشة نفسها أو من متغيرات بيئة معزولة، لا من ثابت في المصدر.

## 0. الخلاصة التنفيذية (TL;DR)

| المحور                         | القرار المقترح في جملة                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| أين تعيش إعدادات SMTP          | **لا في `app_identity_settings` ولا في `app_settings`**. جدول **ناقلات** مستقل `public.notification_transports` (صف واحد مفعّل في المرحلة الأولى) بحقول عمودية مكتوبة، لأن دورة حياة سرّ/علامة تجارية/تهيئة تشغيلية لا تختلط مع بعضها.                                                                                                                                                                          |
| كلمات المرور والمفاتيح         | **ممنوع أن تُخزَّن في عمود نصّي في أي جدول**. تذهب إلى جدول أسرار مُفرَّغ `public.notification_transport_secrets` يحمل **CipherSuite معماة فقط** (`bytea` + رقم مفتاح + منحف + بصمة)، مع منع صريح لـ `jsonb` في نوع العمود.                                                                                                                                                                                     |
| `group_slug` «معماة»؟          | **لا**. `group_slug` مساحة أسماء تنظيمية لا سياج أمني؛ البوابة الوحيدة هي `is_public` + سياسة الجدول + الامتيازات. أي تصميم يخلط بينهما يفشل عند أول `select *`.                                                                                                                                                                                                                                                |
| استراتيجية التشفير             | **طبقتان**: (1) **الحد الأدنى المقبول الآن**: `pgsodium.crypto_secretbox` (XSalsa20-Poly1305 — تشفير مُوثَّق) مع مفتاح في `supabase_vault` ومرجع `key_id` لا نص مفتاح، و(2) **الهدف الاستراتيجي للقالب**: **تغليف المظروف (Envelope Encryption)** بمفتاح DEK **خارج قاعدة البيانات كلياً** (متغير بيئة في نقطة الإرسال / KMS) بحيث لا توجد أي دالة SQL قادرة على فك التشفير. التوصية النهائية في §1.5.          |
| من يُشغّل SMTP فعلياً          | **لا قاعدة البيانات**. لا يوجد `utl_tcp` ولا اتصال صادر من PostgreSQL؛ التصميم: قاعدة البيانات = مخزن التهيئة والقوالب والتدقيق، و**Edge Function/Worker = نقطة التشفير والفك والإرسال**. هذا يحررنا من مزود ثابت ومن قيود شبكة قاعدة البيانات معاً.                                                                                                                                                            |
| جدول القوالب                   | `public.notification_templates` — **صف لكل (مفتاح · لغة · إصدار)**، ثنائي اللغة بصفين لا بعمودين، **بغير قابل للتعديل بعد التنشيط** (immutability) + طراز `draft → active → archived`، وقائمة متغيرات بيضاء موقّعة داخل `variables jsonb`.                                                                                                                                                                      |
| محرك الاستبدال                 | **مُجزّئ أحادي المسار (single-pass tokenizer)** بنمط حرفي صارم `{{snake_case}}`، **بلا تعشيق وبلا تعبيرات وبلا تنفيذ**، مع **تهريب سياقي (contextual auto-escaping)** عند الإخراج، و**فشل صريح (strict)** عند متغير مفقود، وبصمة `sha256` للمخرَج تضمن **idempotency** إعادة الإرسال.                                                                                                                           |
| الحقن                          | الخطر الحقيقي ليس «SQL» (المحرك لا يبني استعلاماً) بل **SSTI/Template Injection + HTML Injection**. علاجه: منع كل بنية غير التعويض في القالب، والتحقق من **نص القالب** و**قيمة المتغير** عند الحفظ **وعند العرض** معاً، وقائمة بيضاء وسوم للبريد، و`iframe sandbox` + CSP في المعاينة الحية.                                                                                                                    |
| RLS                            | `enable + force row level security` على كل الجداول الجديدة · **صفر سياسة كتابة** لـ `anon`/`authenticated` · `revoke all ... from public, anon` · `select` محدود على الجدول العلني المُقنَّع فقط · `service_role` هو المالك الوحيد للأسرار · **RPC بـ `SECURITY DEFINER` هي مسار الكتابة الوحيد**، مربوطة بـ `settings.manage` (للناقل) و`notifications.manage` (للقوالب) عبر مساعدَي صلاحية قابلَين للاستعلام. |
| تسرّب كلمات المرور عبر الرسائل | قرار معماري مُلزِم: **تضمين قيم الإدخال في رسائل الأخطاء** ثغرة قائمة بذاتها في PostgreSQL. العقد: لا `RAISE` يحمل قيمة مستخدم، والتحقق المُسبق قبل أي قيد، مع `EXCEPTION` مُعيدة التجميع في نهاية الدالة.                                                                                                                                                                                                      |
| الواجهة                        | نمط الشاشة الخامسة نفسه: حاوية `@container` واحدة تخدم كل المقاسات. عريض: **قائمة أحداث ← محرّر ← معاينة حية** (3 أعمدة)، أوسط: **2**، هاتف: **عمود واحد** مع مبدّل `محرّر/معاينة` وقائمة أحداث تتحول إلى مُحدِّد شرائطي. المعاينة **لا تُصغَّر بالـ media query بل بمقياس `zoom`/`transform`** على حاوية ثابتة 640px.                                                                                          |
| Realtime                       | إشارة إبطال فقط (نفس قرار شاشة الهوية): قناة على `notification_templates` لـ `authenticated` الممتلِك للصلاحية، لإبطال كاش `['notification-templates']` — **لا بثّ على جدول الأسرار إطلاقاً**.                                                                                                                                                                                                                  |
| التدقيق                        | إعادة استخدام `settings.updated` عند الإمكان، مع امتداد `alter type ... add value` (النمط المعتمد في الترحيلين `160000` و`140000`) لقيم جديدة: `email.transport_updated` · `email.credentials_rotated` · `email.test_sent` · `notification.template_updated` · `notification.template_previewed`. **الـ metadata حقول وأسماء فقط، أبداً قيم.**                                                                  |
| بوابة ما بعد الاعتماد          | قائمة تحقّق إلزامية (§7) فيها بند حاسم: **تأكيد أن منافذ SMTP (25/465/587) غير محجوبة في طبقة الشبكة لدى Supabase**؛ إن كانت محجوبة فالناقل البديل هو HTTPS API للمزوّد، والتصميم لا يتغير لأنه لا يعرف المزود أصلاً.                                                                                                                                                                                           |

## 0.1 حالة النظام الحالية (ما نبني فوقه، لا ما نتجاهله)

هذه الشاشة هي **الثالثة** التي تُضاف فوق نواة جاهزة؛ إهمال الموجود هو ما يكسر المشاريع القالبية.

| الموجود اليوم في المستودع                                                                                                                                                                                     | الأثر المباشر على هذه الشاشة                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `public.app_settings (key, group_slug='general'/'appearance'/'notifications', value jsonb, is_public bool, updated_by, updated_at)` — مفتاح/قيمة                                                              | هو المستودع المقصود للإعدادات **غير السرّية**. مفاتيح التنبيهات الحالية (`notifications.enabled`, `notifications.channels`, `notifications.retention_days`) صالحة للبقاء فيه كما هي. **ما لا يصلح له**: أي شيء سرّي (قيمة `jsonb` نصية صريحة كاملة القراءة لمن يملك `select`) وأي شيء يحتاج تحققاً تركيبياً أو قيداً على عمود.               |
| سياسة `app_settings`: قراءة `using (is_public or is_admin())` + `grant select ... to anon`                                                                                                                    | **`is_public` هي السياج الوحيد**. إضافة مفتاح سرّي بـ `is_public=false` آمن نظرياً، لكنه لا يُبنى عليه أي شيء: `update ... set is_public=true` متاح لمن يملك الكتابة، والـ `value jsonb` يظهر كاملاً في سجلات التدقيق إن لم نُطبّعها. لا نُمرّر أسراراً من هنا إطلاقاً.                                                                      |
| `public.app_identity_settings` — صف فريد مكتوب بحقول، `force row level security`، قراءة عامة، كتابة عبر `admin_update_app_identity` فقط                                                                       | **النمط المعماري الصحيح الذي سنكرّره** (هوية مكتوبة + RPC وحيدة + منع كتابة مباشر) — لكن **الجدول نفسه ليس مكاناً لإعدادات البريد**: قراءته عامة (`app_identity_public_read using (true)`)، وهو مُنشَر في `supabase_realtime` كمصدر حقيقة للشعار والاسم، أي إضافة أسرار أو أرقام منافذ إليه تُلوّث عقد القراءة العام وتُوسّع سطحه بلا مقابل. |
| مساعدا صلاحية موجودان بنمط موحّد: `can_manage_app_identity()` و`can_manage_appearance()` = `is_active_user() and (is_admin() or has_permission('settings.manage'))` مع `revoke ... from public, anon`         | نضيف **نفس القالب حرفياً**: `can_manage_email_transport()` (على `settings.manage`) و`can_manage_notification_templates()` (على `notifications.manage`) — لا نبتكر آلية جديدة، والواجهة تستعلم عنهما لتُقفل المحرّر لا لتُؤمِّنَه.                                                                                                            |
| `permissions` في الـ seed فيها **`notifications.manage` (وحدة `app`)** مُمنوحة لـ `admin`، و`settings.manage` كذلك                                                                                            | لا حاجة لبذر صلاحية جديدة. **التقسيم الطبيعي الجاهز**: بيانات الاتصال/المصادقة = `settings.manage` (لأنها إعداد النظام العام)، والقوالب/قواعد الإرسال = `notifications.manage` (لأنها محتوى سلوكي). هذا يُتيح عمداً تفويض موظف محتوى على القوالب دون مفاتيح السيرفر — وهو بالضبط ما يجعل القالب قابلاً لإعادة الإنتاج لدى عميل نهائي.        |
| `audit_action` enum + `write_audit_log(...)` SECURITY DEFINER مُقيّدة الامتيازات، ونمط `alter type ... add value if not exists` مستخدم فعلاً                                                                  | التوسعة معتادة وآمنة (قيمة في آخر الـ enum ⇒ لا إعادة كتابة للفهارس/الجدول). سنحتاج 4–5 قيم جديدة (المُصفوفة في §3.6) — **بشرط واحد**: أن تُلحق بالذيل لا أن تُدرج في الوسط.                                                                                                                                                                 |

| Realtime مُنشَر على `workspaces` و`app_settings`، وعلى `profiles`                                                                                                                                             | هناك سابقة «إشارة إبطال» لا «بث محتوى». نضيف `notification_templates` فقط، و**نستثني جدول الأسرار صراحةً** من أي منشور.                                                                                                                                                                                                                      |

| `scripts/configure-production-environment.sh` + متغيرات `.env.example` (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_APP_NAME`, `VITE_APP_URL`)                                                       | عقد البيئة للقالب: `VITE_APP_URL` هو **مصدر بناء `{{action_url}}`** الوحيد الموثوق (لا يُخزَّن رابط الفعل في القاعدة كسلسلة كاملة). أي مفتاح تشفير **لا يُضاف هنا إطلاقاً** (انظر §1.7).                                                                                                                                                     |
| `src/i18n/locales/{ar,en}.ts` + `LocalizationProvider` (اللغة/الاتجاه/المنطقة الزمنية كعقد نظام)                                                                                                              | القوالب ثنائية اللغة تستهلك نفس العقد: اللغة تُحلّ من تفضيل المستلم ثم الافتراضي النظامي، والاتجاه يحدد قالب التنسيق (وليس لغة الرسالة فقط).                                                                                                                                                                                                 |
| `SettingsPage` يعرّف `SECTIONS.notifications` بـ `Bell` ويضع `EmptyState`                                                                                                                                     | لا قرارات توجيه جديدة مطلوبة؛ الشاشة تُركَّب في نفس الخانة، ونفس عقد `titleKey/descriptionKey`.                                                                                                                                                                                                                                              |
| `src/lib/branding.ts` + لقطة `localStorage` + سكربت إقلاع مضاد للوميض                                                                                                                                         | **قناة الحقن الوحيدة التي سنعيد استخدامها**: ترويسة الرسالة (الاسم والشعار) تأتي من `app_identity_settings` عبر نفس المسار — أي شاشة التنبيهات **لا تخزّن نسخة مناسَبة من اسم التطبيق** داخل القالب، بل تحقنها وقت الإرسال.                                                                                                                  |

**خلاصة المسح:** النواة جاهزة تماماً؛ الناقص هو (أ) لا يوجد أي جدول ناقلات/أسرار، (ب) `pgcrypto` فقط بدون `pgsodium`/`vault`، (ج) لا يوجد مسار تنفيذ خارجي (لا Edge Function للإرسال حتى الآن)، (د) لا يوجد محرّك قوالب. القرارات الأربعة في §6 تُغلق هذه الفجوات.

# المحور الأول — هندسة قاعدة البيانات وتشفير بيانات السيرفر (SMTP & Encryption)

## 1.1 صياغة المشكلة الأمنية الصحيحة

قبل اختيار الجدول، يجب تثبيت **من نحمي بياناتنا منه؟** وإلا كنا نصف حل تقني لمشكلة مُعرَّفة خطأ. التهديدات بترتيب واقعية الاحتمال في نظام مثل ours:

| #   | المهاجم / السيناريو                                                       | هل يحمي منه «التخزين في جدول سرّي»؟                                  | ما الذي يحمي فعلاً                                                                |
| --- | ------------------------------------------------------------------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| T1  | مفتاح `anon` مُسرَّب (في حزمة نشر أو مستودع) + استعلام REST مباشر         | **نعم، بشرط** أن تكون القراءة محظورة بالسياسة لا بالطمس في الواجهة   | RLS + `revoke` + صفر سياسة قراءة على جدول الأسرار                                 |
| T2  | جلسة مستخدم مصادَق (مدير عام/محرر) تحاول `select` على جداول ليست من شأنه  | **نعم**                                                              | RLS على مستوى الجدول + Force                                                      |
| T3  | جلسة `service_role` مُسربة (أو واجهة إدارة Supabase/SQL Editor بيد مهاجم) | **لا** — يقرأ كل شيء بما فيه النصوص                                  | لا حل داخل القاعدة؛ الحل أن **النص الصريح غير موجود في القاعدة أصلاً** (§1.4–1.5) |
| T4  | لقطة/نسخة احتياطية مسروقة (`pg_dump` من جدول الأسرار)                     | **نعم إن كان النص مُعمّى، لا إن كان `pgcrypto` بمفتاح داخل القاعدة** | مفاتيح خارج القاعدة (vault/KMS/متغير بيئة) ⇒ اللقطة بلا قيمة                      |
| T5  | حقن عبر رسالة خطأ (قيمة السرّ تعود في `error.message` إلى المتصفح)        | **لا علاقة له بالجدول**                                              | عقد أخطاء صارم (§3.4)                                                             |
| T6  | تسرّب عبر `audit_logs.metadata` أو `pg_stat_statements` أو سجلات وسيطة    | **لا**                                                               | عدم تسجيل القيم + عدم وضع مفتاح داخل نص العبارة SQL (§1.4)                        |
| T7  | موظف داخل المشروع (Insider) يملك صلاحية إدارة                             | جزئياً                                                               | فصل الصلاحية (ناقل ≠ قوالب) + تدقيق + تدوير المفاتيح + «الكتابة فقط، لا القراءة»  |

**النتيجة الحاكمة:** أي استراتيجية «نُعمّي كلمة المرور داخل `app_settings`» تعالج T1 فقط وتترك T3/T4/T6 مكشوفة. لذلك نفصل **ثلاثة مخازن ذات أدوار مختلفة** بدل البحث عن «مكان آمن» واحد.

## 1.2 القرار المعماري: ثلاثة مخازن، لا جدول واحد

                                    │                                │

```

### 1.2.1 `public.notification_transports` — لماذا جدول ناقلات وليس «صفّاً واحداً في جدول الهوية»

| ------------------------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### 1.2.2 ماذا لو أردنا «الصف الفريد الموحد» رغم ذلك؟ (مقارنة صريحة)

| المعيار                                          | singleton مكتوب (نمط الهوية)                                                                                                           | ناقلات متعددة + `is_default` (المقترح)         | KV في `app_settings`  |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | --------------------- |
| سرعة التنفيذ                                     | الأعلى (ترميز مألوف)                                                                                                                   | متوسطة                                         | عالية لكنها دَين تقني |
| صرامة التحقق                                     | ممتازة                                                                                                                                 | ممتازة                                         | ضعيفة                 |
| فصل دورة الحياة                                  | سيئ إن ضُمَّت الهوية للبريد                                                                                                            | ممتاز                                          | متوسط                 |
| قابلية إعادة الإنتاج (SMTP + API + مزود احتياطي) | محدودة                                                                                                                                 | ممتاز                                          | محدودة                |
| تعقيد الواجهة                                    | أبسط                                                                                                                                   | تحتاج مُحدِّد ناقل (يُعرض كقائمة جانبية صغيرة) | أبسط                  |
| **التوصية**                                      | **مقبول كـ «شكل» الجدول لو أصررنا على صف وحيد** — أي `notification_transports` بصف واحد مضمون بفهرس فريد جزئي، دون المساس بفصل الأسرار | **المعتمد مقترحاً**                            | مرفوض                 |

الصيغة التوفيقية العملية: **نبدأ بصف وحيد** (`default-smtp`) داخل جدول ناقلات متعدد الصفوف؛ التكلفة الإضافية = فهرسان و`where is_default`، والمكسب = عدم الحاجة لترحيل مخطط لاحقاً. هذا هو «أرخص تأمين مستقبلي» في المشروع.

## 1.3 طبقة الأسرار: شكل المخزن

| العمود                  | النوع                                                                    | الدور                                                                                                                            |
| ----------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| `transport_id`          | uuid PK/FK → transports `on delete cascade`                              | سرّ واحد لكل ناقل (توسعة لاحقة: `+ secret_kind` لتعدد المفاتيح)                                                                  |
| `secret_ciphertext`     | **`bytea` — والنوع مُقيَّد** بـ `pg_typeof(secret_ciphertext) = 'bytea'` | **ممنوع `text`/`jsonb`**: النص في `jsonb` قابل للظهور في السجلات والتطبيع، و`bytea` لا يُعرَض كمحتوى قابل للقراءة في أدوات كثيرة |
| `wrapped_key`           | bytea nullable                                                           | في نمط المظروف: DEK مُغلَّف بمفتاح KMS (انظر §1.5 مسار B)                                                                        |
| `kms_key_id`            | text nullable                                                            | مرجع مفتاح خارجي (ARN/معرّف) — **معرّف فقط، لا مادة مفتاح**                                                                      |
| `key_id`                | uuid                                                                     | مرجع مفتاح `vault.decrypted_secrets` عند مسار A                                                                                  |
| `cipher`                | text check                                                               | `xsalsa20-poly1305` (pgsodium secretbox) \| `aes-256-gcm` (تطبيق Node) \| `chacha20-poly1305` — **قائمة مغلقة، لا AEAD غريب**    |
| `nonce` / `tag`         | bytea                                                                    | منحف فريد لكل عملية (و`tag` منفصل إن استُخدم AEAD يدوياً). **قاعدة:** لا إعادة استخدام منحف مع مفتاح                             |
| `content_fingerprint`   | text check `^[0-9a-f]{64}$`                                              | `sha256` للنص الصريح — **للمقارنة فقط** («هل تغيّر السرّ فعلياً؟» و«هل هذا هو المفتاح الصحيح؟»)، تُعرض أول 8 خانات في الشاشة     |
| `encoding`              | text                                                                     | `utf8-bytes` — يمنع غموض المحارف العربية في كلمة المرور (خطأ شائع: `to_bytes` على UTF-8 != latin1)                               |
| `rotate_by`             | timestamptz nullable                                                     | سياسة عمر السرّ؛ الشاشة تعرض تنبيهاً عند تجاوزه                                                                                  |
| `created_at/created_by` | —                                                                        | سجل الاستبدال (كل تحديث صف جديد أو version bump، لا `update` صامت)                                                               |

**الخواص الأمنية للجدول (عقد، لا كود):**

1. لا سياسة RLS تمنح قراءة لـ `anon`/`authenticated` إطلاقاً — **عدم وجود سياسة = منع** بعد `force row level security`.
2. `revoke all on table ... from public, anon, authenticated` ثم `grant select, insert, update to service_role` فقط.
3. **لا يُضاف إلى `supabase_realtime`** — وإلا صار الـ `update` منقولاُ لكل عميل.
4. **trigger حارس** يرفض أي `insert/update` لا تكون فيه `secret_ciphertext` ناتج دالة تشفير معروفة (فحص طول/بنية الـ bytea + وجود `cipher` و`nonce` غير حاليين) — يمنع «خطأ مطوّري» أن يكتب نصاً صريحاً في عمود معمّى.
5. `comment on column` على كل عمود حساس يوضح أن قيمته **غير قابلة للعرض** — حماية للفرق القادمة التي ستقرأ المخطط.

## 1.4 لماذا ليس «pgcrypto + مفتاح في القاعدة»؟ (نقد الخيار الساذج)

الجملة المعتادة «نستخدم `pgp_sym_encrypt(value, current_setting('app.secret_key'))`» تنهار أمام أربع حقائق:

| الفرضية            | الحقيقة                                                                                                                                                                                                                                |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| المفتاح آمن في GUC | `SET app.secret_key='...'` **يظهر نصه في نص العبارة** → يُلتقط في `pg_stat_activity`، وفي `log_statement`/`auto_explain`/`pg_stat_statements` إن كانت مُفعّلة، وفي سجلات وسيط PgBouncer/pgcat. لا يوجد «إعداد جلسة» سري في PostgreSQL. |
| الدالة الخاصة آمنة | أي دالة `SECURITY DEFINER` تملك حق القراءة ⇒ أي جلسة **أخرى** تستطيع استدعاءها إن امتلكت EXECUTE. لذا: `revoke execute from public, anon` + `grant` انتقائي، تماماً كنمط `write_audit_log` القائم.                                     |
| التشفير يكفينا     | المفتاح داخل نفس القاعدة ⇒ **سرقة اللقطة تعني فك التشفير فوراً** (المفتاح والـ ciphertext معاً). هذا يترك T3/T4 مكشوفين.                                                                                                               |
| pgcrypto قوي       | `pgp_sym_*` جيد لكنه ثقيل/بطيء ولا يمنحنا «معرّف مفتاح» ودوران نظيفاً؛ و`crypt()` للهاش لا التشفير القابل للفك (غير صالح لكلمة مرور نحتاج أن نتكلم بها). ⇒ نحتاج **AEAD مُوثَّقاً بمعرّف مفتاح**.                                      |

كما أن `pgcrypto` مُفعّل لدينا **فقط** لأغراض `gen_random_uuid()`/`digest()`؛ لا نوسّع دائرته ليعمل كطبقة أسرار.

## 1.5 استراتيجيتا التشفير المرشّحتان — والقرار

### مسار A — «داخل القاعدة»: `pgsodium.crypto_secretbox` + `supabase_vault`

البنية: مادة المفتاح تعيش في `vault.secrets` (والجدول محمي بالعضوية في أدوار `pgsodium_keyiduser`/`pgsodium_keyholder`، ولا يُقرأ إلا عبر `vault.decrypted_secrets`)، وكل ما نخزنه في جدولنا هو **`key_id`** لا المفتاح.

```
   RPC admin_update_email_transport(p_password text, …)
        │  (1) فحص الصلاحية · (2) تحقق الأنماط · (3) حصر القيم في نطاق آمن
        ▼
   pgsodium.crypto_aead_…  /  crypto_secretbox(plaintext, nonce, key)
        │            ▲
        │            └── vault.decrypted_secrets(v_key_id)   ← المفتاح لا يظهر في نص العبارة
        ▼
   notification_transport_secrets(secret_ciphertext, key_id, nonce, cipher,
                                  content_fingerprint, secrets_version+1)
        ▼
   write_audit_log('email.transport_updated', …, metadata = {field names + fingerprint prefix})
   ── commit ذرّي واحد ──
```

| ما يكسبه                                                                                         | ما لا يكسبه                                                                                                                                                              |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| لا نص صريح في أي جدول ولا في أي عبارة SQL؛ لا مفتاح في نص العبارة (مرجع `key_id` فقط)            | **أي جلسة تملك استدعاء الدالة المفكِّكة** (أو `superuser`/موظف مشغّل الاستضافة يملك `ALTER ROLE … SET pgsodium.trusted_mode`) تستطيع استخراج النص                        |
| يبقى كل شيء داخل معاملة واحدة: تحقق + تشفير + كتابة + قفل تفاؤل + تدقيق                          | التشفير بلا KMS ⇒ لقطة + وصول DBA = فك مباشر                                                                                                                             |
| أبسط تنفيذ، بلا طبقة خارجية جديدة، ويتوافق مع «لا مزود ثابت»                                     | `pgsodium` ليس مُفعّلاً اليوم؛ يحتاج إتاحته في المشروع المستهدف (في Supabase مُتاح، لكن **هذا افتراض مشروع لا حقيقة عالمية** ⇒ يجب أن يكون مسار B ممكناً بلا تغيير مخطط) |
| وضع `pgsodium.trusted_mode` + `zeroize_secrets` يقلص نافذة بقاء المفتاح في الذاكرة داخل المعاملة | **لا يوجد** أي «مفتاح خارج القاعدة» ⇒ لا يُلبي مطلب «لا يستطيع أي مستخدم مصادق استخراج كلمة المرور» إلا بقيد: **لا تُعرَض أي دالة فك للعميل مطلقاً**                     |

**شرط اعتماد A:** أن تكون **كل** عمليات القراءة المُفكِّكة محظورة على أدوار API وأن لا ينفذ الإرسال من القاعدة (انظر §1.6). أي استثناء — مثل «RPC تعيد نسخة مختبرة من كلمة المرور» — يهدم النموذج كله. لذا: **لا RPC تُعيد نصاً صريحاً أبداً؛ تُعيد `has_password: true`, `fingerprint: "9f2c…"`, `updated_at`** فقط (حقل **write-only** في الواجهة).

### مسار B — «المظروف»: التشفير خارج القاعدة + DEK من KMS/متغير بيئة (الهدف الاستراتيجي)

```
   Admin UI ──(HTTPS, Bearer)──► Edge Function / Worker  «mail-gateway»
                                     │  master key = KMS CMK  أو  متغير بيئة سري (لا يُقرأ من القاعدة)
                                     │
                                     ├─ (1) encrypt(password) → AES-256-GCM  {ct, iv, tag, key_version}
                                     ├─ (2) rpc('admin_store_email_transport', ciphertext...)  ← service_role
                                     │        └─ القاعدة تخزن bytea معمّى فقط (لا dcode دالة فيها)
                                     └─ (3) عند الإرسال: read transport+secret → decrypt in-memory
                                              → SMTP/HTTPS API (provider adapter) → send → log result
```

| ما يكسبه                                                                                                                                                       | ثمنه                                                                                                              |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **لا يمكن لأي دور قاعدة بيانات — ولا `superuser` ولا `service_role` مُسرب — أن يستخرج النص الصريح**، لأن مادة المفاتيح خارج القاعدة. يُلبي مطلب الدراسة حرفياً | طبقة تشغيل إضافية (دالة/خادم) يجب تأمينها: شبكة، أسرار، حدود تنفيذ، سجلات نظيفة                                   |
| دوران مفتاح نظيف (KMS re-wrap) بلا إعادة تشفير كامل، و`key_version` مرئي في القاعدة                                                                            | الكتابة لا تعود «RPC مباشرة من المتصفح» بل تمر بنقطة وسيطة — يجب الحفاظ على التدقيق داخل نفس المسار (الفحص في §7) |
| مزيج مثالي لـ«قالب متعدد العملاء»: كل عميل مفتاحه الخاص                                                                                                        | لا يمكن كتابة السرّ داخل معاملة `UPDATE` واحدة مع بقية الحقول؛ يحتاج عقد «خطوتان + idempotency key» (§1.8)        |
| يفتح الباب نفسه لـ `https_api` (SendGrid/Resend/SES) بلا أي تعديل مخطط                                                                                         | —                                                                                                                 |

### القرار المُوصى به: **B مع واجهة تخزين متطابقة مع A** (مسار تبنٍّ على مرحلتين)

1. **المخطط نفسه في الحالتين**: `notification_transport_secrets` يحمل `CipherSuite` (نص معمّى + رقم إصدار مفتاح + nonce + بصمة). عمود `wrapped_key/kms_key_id` يبقى `null` في مسار A ويُستخدم في B ⇒ **الانتقال من A إلى B تهيئة لا ترحيل**.
2. **المرحلة الأولى تنفيذياً**: A (pgsodium+vault) — لأن المشروع لا يملك حتى الآن أي Edge Function إرسال، ولأن A يُنهي «الألم الفوري»: لا قراءة من `anon`, لا قراءة من `authenticated`, لا نص في اللقطات التي يملكها الفريق.
3. **بوابة إلزامية قبل إعلان A «نهائياً»**: سؤال واحد للمشغّل — «هل يستطيع أي دور SQL غير مالك الجدول استدعاء دوال فك التشفير؟» إن كان الجواب «نعم/غير معروف» ⇒ ننتقل إلى B فوراً قبل أول بريد حقيقي في الإنتاج.
4. **قاعدة لا تُكسر في أي مسار:** `{{smtp_password}}` **ليست متغيراً في القوالب أبداً**، ولا تُدرَج في أي معاينة، ولا في `notification_transports.config`.

# المحور الثاني — محرك قوالب الرسائل واستبدال المتغيرات (Template Tokenizer Engine)

## 2.1 جدول `public.notification_templates` — التصميم

**الفلسفة:** القالب **أصل برمجي محتوم** (piece of content-as-code): يحتاج إصدارات، مراجعة، تجميداً بعد النشر، وبصمة تكفل أن «ما رأيته في المعاينة هو ما سيُرسل». ومن هنا جاءت قرارات عدم القابلية للتعديل (immutability) والفصل اللغوي بالصفوف.

| الحقل                                         | النوع                 | الدور والقيود                                                                                                                                                                                                |
| --------------------------------------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `id`                                          | uuid PK               | —                                                                                                                                                                                                            |
| `key`                                         | text                  | **معرّف حدث النظام**: `auth.welcome_invitation`, `security.suspension_alert`, `backup.failure_notice`, …؛ نمط `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*){1,3}$` (نطاق.حدث) — قابل للتوسيع لكل مشروع قالب دون ترحيل |
| `channel`                                     | text check            | `email` \| `in_app` \| `sms` \| `webhook` — يُبقي الجدول **قوالب رسائل** لا «قوالب بريد» فقط                                                                                                                 |
| `locale`                                      | text                  | `'ar'` \| `'en'` + check على قائمة اللغات المعتمدة (نفس عقد `profiles.preferred_locale`/`appearance.default_locale`)                                                                                         |
| `version`                                     | int                   | `>= 1`؛ **يزداد لا يُستبدل**                                                                                                                                                                                 |
| `status`                                      | text check            | `draft` \| `active` \| `archived`                                                                                                                                                                            |
| `is_current`                                  | boolean               | وحيد لكل `(key, locale)` عند `status='active'` (فهرس فريد جزئي + حارس)                                                                                                                                       |
| `subject_ar` / `subject_en`?                  | —                     | **لا**: الفصل بالصفوف يكفي، وعمودان = ازدواجية. لكل صف `subject` **بلغته**                                                                                                                                   |
| `subject`                                     | text                  | 1..200 + منع `[[:cntrl:]]`؛ **لا وسوم HTML داخل العنوان** (قيد صريح `not ~ '<'`)                                                                                                                             |
| `body_text`                                   | text                  | نسخة النص المجرد (إلزامية للبريد) — خط أمان أخير إن رفض العميل HTML، وضرورية لـ `text/plain` multipart                                                                                                       |
| `body_html`                                   | text nullable         | نسخة HTML **مقيدة بقائمة بيضاء** (§2.5)                                                                                                                                                                      |
| `layout_key`                                  | text nullable         | مرجع لقالب تخطيط عام (`base_email_default`) بدل تكرار الهيكل في كل قالب — يُفعَّل عند الحاجة فقط (انظر §2.8)                                                                                                 |
| `direction`                                   | text check            | `rtl` \| `ltr` — مشتق افتراضياً من اللغة وقابل للتثبيت                                                                                                                                                       |
| `variables jsonb`                             | jsonb                 | **المتغيرات البيضاء**: `[{name, type, required, max_length, pattern?, default_strategy?}]` (§2.3)                                                                                                            |
| `sample_variables jsonb`                      | jsonb                 | بيانات مُلغّمة للعرض فقط («لينان», `user@example.invalid`) — **تُستخدم في المعاينة بدل بيانات حقيقية**، فلا PII تدخل المحرّر                                                                                 |
| `requires_tokens`                             | boolean               | `true` ⇒ يُسمح بـ `{{action_url}}` **فقط** إذا كان المُرسِل سيمرّر توكن توقيع صحيح؛ يمنع روابط فعل مكسورة                                                                                                    |
| `content_hash`                                | text `^[0-9a-f]{64}$` | `sha256(subject‖body_text‖body_html‖variables)` — يُخزَّن ويُقارَن؛ يُمكّن «لم يتغير شيء ⇒ لا إصدار جديد»                                                                                                    |
| `notes`                                       | text nullable         | سبب التغيير (مراجعة بشرية)                                                                                                                                                                                   |
| `created_at/updated_at/created_by/updated_by` | —                     | نمط الجداول القائم + `set_updated_at()`                                                                                                                                                                      |

**المفاتيح والفهارس:** قيد فريد `unique (key, locale, version)`؛ فهرس فريد جزئي `(key, locale) where status='active' and is_current`؛ فهرس `(key, locale, version desc)`؛ فهرس `lower(key)` عند الحاجة؛ قيد `check (channel <> 'email' or body_text is not null)` (كل بريد يحتاج نسخة نصية).

### 2.1.1 لماذا صفا لكل لغة وليس عمودَي `name_ar/name_en`؟

| المعيار                             | صف لكل (key, locale, version)                                             | عمودان لكل لغة                               |
| ----------------------------------- | ------------------------------------------------------------------------- | -------------------------------------------- |
| عدد اللغات مستقبلاً (`fr`, `tr`…)   | **صفر ترحيل** — إضافة قيمة check                                          | ترحيل مخطط في كل مرة                         |
| القوالب غير المترجمة (ترجمة متأخرة) | `insert` صف `en` فقط؛ السقوط للغة الاحتياطية منطق واضح                    | أعمدة `null` مبعثرة وسؤال «هل 0 = لا ترجمة؟» |
| عدم قابلية التعديل والإصدارات       | مجموعة إصدار = `key + version`؛ التفعيل/التراجع ذرّي عبر قلب `is_current` | أصعب                                         |
| التطابق مع `roles(name_ar,name_en)` | لا يتطابق، **وبشكل مقصود**: هذه محتوى لا أسماء عرض                        | يتطابق ظاهرياً فقط                           |
| **الحكم**                           | **معتمد مقترحاً**                                                         | مرفوض (يُقفل النظام على لغتين إلى الأبد)     |

**سلوك السقوط (fallback) عقده صريح:** طلب `locale='fr'` ⇒ `active(fr)` ← `active(ar)` (لغة النظام الافتراضية من `appearance.default_locale`) ← `خطأ` إن لم يوجد أي نشط. القاعدة **لا تُترجم نصاً**، ولا يوجد ترجمة آلية في هذه الشاشة.

### 2.1.2 عدم القابلية للتعديل (immutability) — لماذا هي جوهر المحرك لا زينة

- **Idempotency الحقيقية** تتحقق فقط عندما تكون الدالة `render(template_version, vars)` نقية وثابتة: رسالة أعيد إرسالها بعد ساعة بسبب فشل مؤقت يجب أن تخرج **بايت-ببايت** مطابقة — وهذا يحمي من تكرار رسائل مختلفة للمستخدم نفسه.
- **المعاينة = الإرسال**: البصمة `content_hash` التي يراها المدير في المعاينة هي نفسها التي تُقيَّد في سجل الإرسال؛ أي اختلاف = حدث أمني.
- **التراجع** = قلب `is_current` إلى الإصدار السابق (ثانية واحدة، بلا بيانات مفقودة).
- التطبيق: **trigger حارس** يرفض `update` على `status='active'` لكل من `subject/body_text/body_html/variables/content_hash`؛ التحرير يُنشئ مسودة جديدة (`draft`, `version = max+1`)، و«نشر» = `active` + ترقية الإصدار السابق إلى `archived` في نفس المعاملة. (الأسلوب نفسه المستخدم في `guard_role_permissions_writes()` — لا نبتكر.)

## 2.2 دورة حياة القالب

```
      admin_update_notification_template(draft)
   ┌──────────────────────────────────────────────────────────────┐
   │                                                              ▼
 [ absent ] ──insert──► [ draft ] ──validate──► [ draft: valid ] ──publish──► [ active · is_current ]
                            ▲                        │                            │        │
                            │                        │ edit ⇒ new draft           │        │ new draft (v+1)
                            └────────────────────────┘                            ▼        ▼
                                                                        [ active v(n) ]  [ archived ]
                                                                                ▲            │
                                                                                └── rollback ┘
   قراءات العميل: draft خاصة بمالكها · active فقط هي المستهلكة وقت الإرسال · archived غير قابلة للاستهلاك
```

| الحالة     | من يكتب                     | من يقرأ                          | استهلاك وقت الإرسال |
| ---------- | --------------------------- | -------------------------------- | ------------------- |
| `draft`    | حامل `notifications.manage` | كاتبه + admin                    | **لا**              |
| `active`   | عبر «نشر» فقط (RPC)         | كل من يملك الصلاحية + RPC_render | **نعم**             |
| `archived` | لا يُعدَّل                  | للعرض/التراجع                    | لا                  |

## 2.3 عقد المتغيرات (Whitelist Schema) — لا «أي شيء داخل `{{}}`»

```
variables: [
  { name: "user_name",   type: "text",  required: true,  max_length: 120 },
  { name: "app_name",    type: "text",  required: true,  max_length: 80,  source: "identity" },
  { name: "action_url",  type: "url",   required: true,  allowed_hosts: ["<VITE_PUBLIC_APP_URL>"], require_https: true },
  { name: "expires_at",  type: "datetime", format: "iso-date-time", required: false },
  { name: "support_email", type: "email", required: false }
]
```

| النوع           | قواعد التحقّق                                                                                                  | نمط الإخراج                                                                                |
| --------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `text`          | طول + منع `[[:cntrl:]]`                                                                                        | **HTML-escaped** في `body_html`، خام في `body_text` (مع طي الأسطر)                         |
| `url`           | بروتوكول `https` (و`http` في التطوير فقط) + مضيف ضمن القائمة البيضاء + **منع** `javascript:`/`data:`/`mailto:` | وسم `<a href>` مُهرَّب الوسائط + ذيل النص ` (التفاصيل: <url>)`                             |
| `email`         | نفس نمط البريد في الجدول الهويّاتي                                                                             | `<a href="mailto:…">`                                                                      |
| `int` / `money` | نطاق                                                                                                           | تنسيق حسب اللغة (أرقام لاتينية/عربية قسرياً حسب `direction`)                               |
| `datetime`      | ISO 8601 قابل للتحليل                                                                                          | يُنسَّق بتوقيت المشروع (`appearance.default_timezone`) ثم `Intl` — **لا تنسيق في القاعدة** |
| `bool`          | —                                                                                                              | يُستبدل بنص مُعرَّف مسبقاً في القالب (لا شروط في المحرك)                                   |

**قواعد صارمة على المتغيرات:**

1. **الحصر**: لا يُسمح بأي اسم خارج `variables[]`؛ المتغير المجهول = **رفض القالب عند الحفظ** و**خطأ عند العرض** (ليس فراغاً).
2. **الحجز**: أسماء محظورة لا تُقبل أبداً: `smtp_password`, `token`, `jwt`, `session`, `cookie`, `api_key`, `service_role`, `anon_key`, `database_url`, وأية قيمة تبدأ بـ `secret`. يمنع أن يطلب محرّر محتوى «أرسل لي كلمة المرور في الإيميل».
3. **`source: "identity"`**: متغيرات تُحقن من `app_identity_settings` وقت الإرسال ولا يقبل المحرّر أن يكتب قيمتها يدوياً (ضمان عدم وجود نسخة مناسَبة من اسم التطبيق).
4. **الطول الإجمالي**: سقف لحجم النص المُخرَج (مثلاً 40 KiB) + سقف لعدد العناصر — يمنع استغلال `{{long_blob}}×N` كـ amplification.
5. **القيم لا تُقرأ من القاعدة** في هذه الشاشة؛ تأتي من المُرسِل (worker) أو من `sample_variables` للمعاينة فقط.

## 2.4 المُجزّئ (Tokenizer): الخوارمية بالمراحل — «مُحلِّل مُهمَل التكرار آمن خادِمياً»

```
   (0) قصّ المُدخلات (subject ≤200, body ≤40KiB)
   (1) تجزئة حرفية بنمط واحد صارم، أحادي المسار، بلا تغشيم (greedy) ولا تعشيق:
          {{  [a-z][a-z0-9_]{0,63}  }}     مع مسافات اختيارية داخل الحاضنتين فقط
   (2) رفض صريح لبنى غريبة (fail-closed، لا تجاهل):
          '{{' غير مُغلقة · '}}' يتيمة · '{{{{' (تعشيق) · '{%' أو '#{' أو '{!' (Jinja/Twig/Freemarker)
          وسوم/تعبيرات: 'script', 'on<word>=', 'javascript:', 'srcdoc', '<iframe'  ⇒ في body_html
   (3) مطابقة كل رمز على whitelist القالب (variables[]) — المجهول ⇒ خطأ (Tpl01)
   (4) تحقّق النوع لكل قيمة (طول/نمط/بروتوكول/مضيف) — الفشل ⇒ خطأ (Tpl02)
   (5) تعويض أحادي المسار على نسخة من النص (لا إعادة مسح للمُخرَج)  ⇒  ★ لا «تكرار حلقة الاستبدال»
   (6) تهريب سياقي (contextual escaping) حسب موضع الاستبدال داخل جسم HTML:
          نص بين وسوم → HTML escape · قيمة داخل خاصية محجوزة → ممنوعة أصلاً (لا استبدال في خصائص)
   (7) بناء المخرَج: subject · body_text · body_html · multipart boundary · content_hash(sha256)
   (8) غلاف RTL/LTR + ترويسة بسيطة (من الهوية) + بديل نصي إلزامي
```

### لماذا «أحادي المسار» هو لبّ الأمان هنا

| نمط محرك                                               | المخاطر                                                                                                       | الحكم                                                                                     |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| تعويض تكراري حتى «لا يبقى `{{`»                        | **تضخيم/تعشيق**: قيمة تحوي `{{app_name}}` تصبح مدخلاً لجولة ثانية (و`{{a}}` ← `{{b}}` ← … = DoS + تسرّب سياق) | **مرفوض**                                                                                 |
| تعويض أحادي المسار على نسخة (المقترح)                  | قيمة المُرسِل **نص لا شفرة**، مهما احتوت                                                                      | **معتمد**                                                                                 |
| محرّكات قوالب كاملة (`{% if %}`, `{{ f() }}`, include) | SSTI ⇒ تنفيذ على الخادم؛ وتحتاج «sandbox» قوي، وتُعيد تعريف الأمان مع كل ترقية مكتبة                          | **مرفوض في هذه الشاشة** (يُضاف لاحقاً فقط على مستوى worker وبمحرّق مُقيَّد، خارج القاعدة) |
| Mustache مع أقسام/شرائط                                | وسائط قياسية لكن تتطلب منطق حل سلاسل، ومخرَج HTML افتراضي غير مُهرَّب إن أُسيء استخدام `{{{ }}}`              | **مرفوض الآن**؛ المنطق الشرطي يُنقل إلى **اختيار قالب آخر** بدل فروع داخل القالب          |

> **قاعدة تصميمية للقالب:** «إن شعرت أنك تحتاج `if` داخل الإيميل، فأنت تحتاج قالباً جديداً». هذا يبقي المحرك صفراً من التعقيد و100% قابل للتدقيق، وهو ما يجعله صالحاً للنسخ إلى مشروع آخر.

### Idempotency — ثلاث طبقات (كلها نتاج التصميم نفسه)

| الطبقة  | الضمان                                                                                                                                                                                                          |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| القالب  | `version` + `is_current` + عدم قابلية التعديل ⇒ نفس المدخلات ⇒ نفس المخرَج أبدياً                                                                                                                               |
| العرض   | `render` دالة **قراءة** (`stable`) لا تكتب شيئاً؛ استدعاؤها 1000 مرة = بصمة واحدة (قابلة للاختبار: اختبار «استقرارية المخرَجات»)                                                                                |
| الإرسال | مفتاح التكرار = `sha256(key ‖ channel ‖ locale ‖ recipient_id ‖ dedupe_window ‖ content_hash)`؛ جدول `notification_deliveries(request_key)` بفهرس فريد يمنع الرسالة الثانية في نفس النافذة (امتداد طوري — §2.9) |

## 2.5 صدّ الحقن: HTML Injection في البريد وفي المعاينة الحية

هنا الخطر مزدوج: **الرسالة المستقبَلة** و**المتصفح المحلي للمحرّر**.

### (أ) في نص القالب (يكتبه المدير)

| الإجراء             | التفصيل                                                                                                                                                                                                                        |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| قائمة بيضاء للوسوم  | `p br strong em b i a ul ol li table thead tbody tr td th h1-h4 blockquote span hr div img` — **والباقي يُرفض لا يُقتلَع** (رفض صريح أفضل من «تنظيف صامت» يُفاجئ المدير)                                                       |
| قائمة بيضاء للخصائص | `href` (على `a`), `src`+`alt`+`width` (على `img`), `align/colspan/rowspan`, `style` **محدود بخاصيات تنسيق آمنة** (لون/حجم خط/حشو/حدود/محاذاة)                                                                                  |
| محظور قطعياً        | `script iframe object embed form input button style link meta base formaction`, معالجات `on*`, `javascript:`/`data:` (عدا `data:image/svg` **ممنوع**، و`cid:` يُسمح فقط إن كان مرفقاً حقيقياً مُعلَماً من المُرسِل), `@import` |
| الروابط             | `href` يجب أن يبدأ بأصل معرّف مسبقاً (`VITE_PUBLIC_APP_URL`) أو قائمة مضيفين بيضاء؛ **لا** `http:` في الإنتاج                                                                                                                  |
| الصور               | بروتوكول `https` + نطاق مُعرَّف (شعار عام من `public-branding`) + `alt` إلزامي (لإنزال الصور في Outlook)                                                                                                                       |
| التحقق في موضعين    | **عند الحفظ** (يظهر الخطأ في المحرّر مع رقم السطر) و**عند العرض/الإرسال** (لا يمكن أن تدخل نسخة مُحرَّفة من مسار API آخر)                                                                                                      |

### (ب) في قيمة المتغيرات

`text` ⇒ **تهريب HTML كامل** (`&`, `<`, `>`, `"`, `'`) ⇒ حتى لو أرسل المُرسِل قيمة تحوي `<script>` أو `</td><td>`, فهي نص معروض لا بنية. و`url` ⇒ تحقق **قبل** أن تُغلَّف في وسم. **لا يوجد** استبدال داخل خاصية HTML مُحرَّرة؛ كل الاستبدال في مواضع نصية فقط — هذا القيد وحده يُلغي فئة كاملة من ثغرات «kinked quote / attribute break».

### (ج) في المعاينة الحية داخل الشاشة

1. **لا `dangerouslySetInnerHTML` في الواجهة إطلاقاً.** المعاينة تُبنى داخل `<iframe sandbox="">` (بلا `allow-scripts`، بلا `allow-same-origin`) بمصدر `about:blank` + كتابة المستند عبر `srcdoc`/`Blob URL`.
2. **CSP خاص بالمعاينة**: `default-src 'none'; img-src https:; style-src 'unsafe-inline'` (لا مفرّ من inline style في البريد)، وبلا `connect-src` ⇒ المعاينة لا تستطيع أن تتصل بأي شيء.
3. **`dir="rtl"` + `lang="ar"`** على جذر المستند المُعايَن، وخط النظام — لتظهر المحاذاة الحقيقية لا المُفترَضة.
4. المعاينة **لا تُنفّذ** أي طلب شبكي لروابط داخلها؛ تُعرض كعناوين نصية (منع «beacon» يتتبع من يفتح المعاينة).

### (د) في البريد المُرسَل (هندسة قابليتها للتسليم)

البريد الآمن لا يعني فقط عدم ثغرة، بل **ألا ينتهي في Spam** (وهذا نصف مهمة «Mail Infrastructure Lead»):

| البند                   | القاعدة                                                                                                                                                                                |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| البنية                  | جدول 640px، **inline styles فقط**، لا `<style>` في `head` (Outlook.com يقتله أحياناً)، لا flex/grid، لا خلفية صور مطلوبة لفهم المحتوى                                                  |
| `multipart/alternative` | `text/plain` ثم `text/html` بترتيب ثابت، وboundary مُولَّد من القاعدة بـ `gen_random_uuid()`                                                                                           |
| المحاذاة                | RTL: `align` صريح + `dir="rtl"` على `body`؛ LTR نسخة منفصلة لا «قلب اتجاه» آلي                                                                                                         |
| المصادقة المُرسِلة      | SPF + DKIM + DMARC على نطاق `sender_email` (تُتحقَّق في `admin_test_email_transport`) — **المزامنة مع نطاق `app_identity_settings.admin_email`** حتى لا يرسل النظام باسم نطاق لا يملكه |
| الأظرف                  | `Return-Path`/`From` على نفس النطاق، لا بريد شخصي                                                                                                                                      |
| المحتوى                 | لا «عنوان كله CAPS» لا مرفقات في الرسائل التجريبية، لا صورة واحدة بلا نص (spambait)                                                                                                    |
| الترويسة القانونية      | رابط إلغاء اشتراك `List-Unsubscribe` **يُبنى من `VITE_PUBLIC_APP_URL` + توكن موقّع** (لا يُخيَّط في نص القالب)                                                                         |
| التوقيع                 | `{{action_url}}` للتفعيل/الدعوة: توكن قصير العمر يوقّعه worker عند الإرسال (HS256/JWT أو opaque token + hash في القاعدة) — **القالب يحمل «اسم الرابط» لا «الرابط مُوَقَّعاً»**         |

## 2.6 أين يعيش المحرّك؟ (العتبة الفاصلة)

```
                    ┌──────────────────────────────────────────────┐
                    │              قاعدة البيانات                  │
   المتصفح ◄──────►│  التخزين · التحقق البنيوي · القوالب · RLS   │
   (محرّر+معاينة)   │  admin_render_notification(...)  ← RPC معاينة│

                    ┌───────────────┴──────────────▼───────────────┐

                    │  tokenizer كامل · تشفير/فك · SMTP/HTTPS API   │
                    │  توليد التوكنات · الترويسات · المرفقات        │
                    └───────────────────────────────────────────────┘

| الموضع                              | المزايا                                                                            | العيوب                                                                                                 | الحكم                                                                                |
| ----------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| **SQL بالكامل** (tokenizer في دالة) | لا طبقة خارجية · idempotency داخل المعاملة                                         | لا HTML sanitization حقيقي في SQL؛ تهريب يدوي محفوف؛ تعقيد صيانة مرتفع؛ لا يمكنه الاتصال بـ SMTP أصلاً | **جزئي فقط**: يُستخدم لـ **التحقق البنيوي + المعاينة** (نص/روابط/متغيرات) لا للإنتاج |
| **Worker بالكامل**                  | مكتبات ناضجة، عزل تام، تحكم بالموارد، كل مزود عبر adapter                          | يحتاج طبقة نشر وأسرار                                                                                  | **معتمد للإرسال النهائي**                                                            |
| **المختلط (المقترح)**               | معاينة فورية داخل المحرّر عبر RPC قراءة فقط، والإرسال الحقيقي من worker بنفس العقد | عقد واحد يجب أن يبقى متطابقاً في المكانين                                                              | **المعتمد**                                                                          |

**شرط تطابق المسارين (مُطبَّق بالاختبار لا بالثقة):** «اختبار ثنائية الطريق» — نفس `(key, locale, version, vars)` ⇒ نفس `content_hash` من RPC المعاينة ومن worker. يُضاف إلى `scripts/audit/database.mjs` كحالة فحص حيّة، لأنه إن تصدّع هذا العقد فالبصمة لا معنى لها.

# المحور الثالث — سياسات RLS وتصميم الواجهة المتجاوبة

## 3.1 نموذج التهديد المُختصَر المُوجِّه للسياسات

نُصفّ سياساتنا لخمسة أدوار فعلية: `anon` (زائر/شاشة دخول), `authenticated` بدرجاته (viewer/editor/admin/super_admin), `service_role` (CI + worker + استيراد الترحيل), و«مشغّل قاعدة البيانات» (تهديد افتراضي يجب أن يظل عاجزاً عن قراءة النص الصريح)، و«مُستولٍ على حزمة الواجهة» (يجد مفتاح `anon` لا أكثر).

## 3.2 مصفوفة السياسات — جدول مصحَّح لكل قرار

| الكائن                                         | `anon`                                               | `authenticated` بدون صلاحية                                      | `authenticated` بحامل `settings.manage`                                | حامل `notifications.manage`                                      | `service_role`                                           |

**الترميز المفاهيمي لقرار السياسة** (عقد، لا SQL):

| #   | القاعدة                                                                                                       | السبب                                                                                                                                                          |
| --- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1  | `enable row level security` **+** `force row level security` على كل جدول جديد                                 | `force` تُسقط حصانة المالك — نفس ما فعلته شاشة الهوية (`ALTER TABLE … FORCE ROW LEVEL SECURITY`) وإلا صار `service_role` المالك متجاوزاً لكل شيء               |
| P2  | `revoke all on table … from public, anon, authenticated` ثم **منح انتقائي**                                   | الافتاح الآمن أولاً ثم فتح ما نحتاجه؛ النمط القائم حرفياً في `20261001150000`                                                                                  |
| P3  | صفر سياسة `insert/update/delete` على أي جدول إعدادات/أسرار                                                    | الكتابة الوحيدة المسموحة هي RPC مُعرَّفة ومُدقَّقة                                                                                                             |
| P4  | صفر سياسة `select` على `*_secrets`                                                                            | لا مسار قراءة يعني لا تسرّب؛ لا حاجة إليه (الواجهة تعرض `has_password`)                                                                                        |
| P5  | كل سياسة قراءة مشروطة بـ `to authenticated` + استدعاء مساعد الصلاحية                                          | `using (public.can_manage_notification_templates())` — لا «`auth.role()='authenticated'`» فضفاض كما في الجداول القديمة؛ نرفع السقف في الجديد ولا نخفضه         |
| P6  | مساعد الصلاحية نفسها `security definer` + `set search_path = pg_catalog, public` + `revoke from public, anon` | منع **search_path hijacking** (نفس ما فُعل في `can_manage_app_identity`) — `set search_path` إلى قائمة قصيرة صريحة لا إلى `''` التي تُعطّل `gen_random_uuid()` |
| P7  | فصل `settings.manage` (ناقل) عن `notifications.manage` (قوالب)                                                | أقل صلاحية كافية لكل عملية؛ يسمح بمحرّر محتوى بلا مفاتيح                                                                                                       |
| P8  | `has_permission('*')` يمر تلقائياً                                                                            | لأن `is_admin()` = `has_permission('*')`؛ super_admin لا يُستثنى ولا يحتاج سياسة منفصلة                                                                        |
| P9  | الحظر على الكتابة المباشرة يُطبَّق بـ `revoke` لا بسياسة «منع»                                                | سياسة `deny` في Postgres غير موجودة (السياسات **OR**)؛ لذا **الغياب** هو الرفض — أي إضافة سياسة `insert` خطأً = ثغرة، وهذا يفسر وجوب فحص المرآة                |
| P10 | لا سياسات «بالاسم/البريد الإلكتروني»                                                                          | الحظر دائماً على **صلاحية** لا على هوية؛ يُبقي النظام قالباً (أسماء الأدوار تتغير من عميل لآخر)                                                                |

## 3.3 الـ RPC كسياج وحيد: خصائص إلزامية

| الخاصية                                                                                 | لماذا هي شرط لا اختيار                                                                                                                                                |
| --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `security definer`                                                                      | لأن العميل لا يملك الامتياز المطلوب؛ لا «`invoker` مع منح أعمدة»                                                                                                      |
| `set search_path = pg_catalog, public`                                                  | يمنع استبدال كائنات عبر schema مُهاجَم؛ **ولا نضع `pg_temp`** (الجدول المؤقت يُخفي أي اسم)                                                                            |
| لا `owner = postgres/superuser` — owner دور مُنخفض الصلاحيات                            | لا نوسع صلاحية الدالة إلى ما لا نحتاج؛ الدالة تحتاج **جدولاً واحداً + مساعد صلاحية + write_audit_log**، لا غير                                                        |
| `revoke execute ... from public, anon` + `grant execute to authenticated, service_role` | الافتراضي في Postgres هو `EXECUTE to PUBLIC`؛ **عدم السحب = ثغرة** حتى مع وجود فحص داخل الدالة (السياسة/الفحص يُقيِّمان القيم، لكن السحب يمنع الفهم الخاطئ للاستدعاء) |
| `transaction_isolation` + «كل شيء في معاملة واحدة»                                      | القالب + `is_current` + audit + version bump إما معاً أو لا شيء (نمط `admin_set_user_status`)                                                                         |
| **فحص الصلاحية كأول سطر**                                                               | كل مسار خطأ لاحق يجب ألا يسبقه كشف أي معلومة                                                                                                                          |
| لا `RAISE` يحمل قيمة                                                                    | §3.4                                                                                                                                                                  |
| قفل تفاؤل بـ `p_expected_updated_at` (و`p_expected_hash` للقوالب)                       | يمنع «آخر من حفظ يفوز» بين مديرَين على نفس الشاشة (نفس عقد شاشة الهوية والمظهر)                                                                                       |
| إرجاع **لقطة مقنَّعة**، لا «عدد الصفوف»                                                 | الواجهة تحتاج حالة ما بعد الكتابة بلا إعادة استعلام (ولا سباق قراءة)                                                                                                  |
| `write_audit_log` داخل نفس المعاملة                                                     | التدقيق الذي لا يُفصل عن الفعل هو التدقيق الوحيد المفيد؛ `entity` ثابت للبحث                                                                                          |

## 3.4 عقد الأخطاء — أهم بند أمني في الدراسة كلها (كثيراً ما يُهمل)

سلوك PostgreSQL الافتراضي: **أي `check` أو `not null` يفشل قد يُعيد قيمته في نص الخطأ**، والسلسلة تعود عبر PostgREST إلى `error.message` في متصفّح المدير. مثال الكارثة: قيد «لا أسرار في `app_settings`» يفشل فيُطبع `value: P@ssw0rd!…` في سجلات الشبكة، وفي Sentry، وفي سجلات Vercel.

**العقد المُطبَّق:**

1. **التحقق اليدوي المُسبَق دائماً قبل أي قيد قاعدة** (أنماط/أنواع/طول/قوائم بيضاء) برسالة تحمل **اسم الحقل فقط**: `…: sender_email is invalid` (بلا قيمة).
2. `exception when others` في **ذيل** الدالة يعيد رفع `raise exception 'email_config_update_failed' using errcode = sqlstate` — **بلا `sqlerrm` خام**. الأخطاء الداخلية لا تُسرَّب؛ تُسجَّل على مستوى التشغيل (worker logs) وتُرتبط بـ `request_id`.
3. جدول أخطاء مطبَّع تستهلكه الواجهة وترجمه من القاموس (نفس أسلوب `LOC02` في شاشة المظهر):

| الرمز    | المعنى               | رسالة المستخدم (ar)                                       |
| -------- | -------------------- | --------------------------------------------------------- |
| `42501`  | لا صلاحية            | «تحتاج صلاحية إدارة الإعدادات/التنبيهات»                  |
| `22023`  | قيمة/نمط غير مقبول   | حقل أحمر + اسم الحقل في المحرّر                           |
| `MAIL01` | صراع قفل تفاؤل       | «حُدِّثت التهيئة أثناء تحريرك» + خيارات: تحديث / نسخ لقطة |
| `MAIL02` | بنية payload         | «بنية الطلب غير صالحة»                                    |
| `MAIL03` | سرّ غير مُتاح        | «مادة التشفير غير متاحة؛ تواصل مع المشغّل» (لا تفاصيل)    |
| `MAIL04` | محاولة سرّ في KV     | «لا يمكن تخزين بيانات اعتماد في الإعدادات العامة»         |
| `TPL01`  | متغير مجهول/مفقود    | «`{{xyz}}` ليس متغيراً معتمداً لهذا الحدث»                |
| `TPL02`  | قيمة متغير غير صالحة | اسم المتغير فقط                                           |
| `TPL03`  | لا قالب نشط          | «لا يوجد قالب منشور بهذه اللغة»                           |
| `TPL04`  | HTML مرفوض           | الوسوم/الخصائص المخالفة مُصفّاة إلى **أسماء** فقط         |
| `TPL05`  | متغير محجوز          | «هذا الاسم ممنوع في القوالب»                              |
| `SEC01`  | مفتاح/دوران          | «إصدار المفتاح غير متوافق — أعد الحفظ بعد التحديث»        |

4. **اختبار إلزامي** (يُضاف إلى `scripts/audit/database.mjs`): «لا تظهر كلمة المرور المُختبَرة في أي استجابة خطأ» — يُدخِل قيمة عشوائية مُعرَّفة `SENTINEL-<uuid>` في كل حقل، ويستدعي جميع حالات الفشل، ويؤكد أن `SENTINEL` **لا تظهر** في `error.message` ولا في `audit_logs.metadata` ولا في أي مسار جانبي. هذا الفحص هو الذي يجعل العقد حقيقة لا نَصاً في مستند.

| **قائمة المتغيرات** | لكل قالب: chips قابلة للإدراج في موضع المؤشر، مع النوع/الإلزامية، وزر «متغير مفقود في النص» يبرزه                                                                                        | المحرّر يرى القالب **والقائمة** معاً؛ لا يُترك يخمّن الأسماء                                                                                                                               |
| **الإصدارات**       | شريط علوي: `v3 active` · «مسودة v4» · قائمة منسدلة «تراجع إلى v2» + diff مختصر (أسماء الحقول وأطوالها)                                                                                   | يُغني عن محرّر diff كامل؛ الـ diff النصي الخام قد يعرض محتوى حساساً                                                                                                                        |
| **المعاينة الحية**  | `iframe sandbox` + مبدّل سطح المكتب/موبايل + مفتاح «نص مجرد / HTML» + «لغة العرض ar/en»                                                                                                  | تُرسم بعد `useDeferredValue` (250ms) من نص المحرّر، و**لا تُرسَل إلى الشبكة**؛ المعاينة التي تريد بيانات حقيقية تمرّ عبر `admin_render_notification(mode:'preview')` بـ `sample_variables` |
| **لوحة التحقّق**    | نتائج `TPL04/TPL05` مع الوسم/الحقل المخالف وموضع السطر                                                                                                                                   | «لماذا لم يُقبل قالبك» مرئي دائماً، لا في الـ console                                                                                                                                      |
| **Realtime**        | قناة على `notification_templates` → إبطال `['notification-templates']` + مؤشر «حدث تغيير» على عنصر القائمة                                                                               | إن كان محرِّراً آخر ينشر الآن، تُظهر الواجهة لافتة صفراء بدل الصمت                                                                                                                         |

### 3.6.4 تدفّق الحالة (TanStack Query) — نفس عقد الشاشات السابقة

```
   useQuery(['notification-transports'])           → admin_get_email_transport (masked snapshot)
   useQuery(['notification-templates', key,locale]) → select مباشر
   mutation: admin_update_email_transport        → invalidation: ['notification-transports']
   mutation: upsert_draft (تفاؤلي: patch local)      → invalidation: ['notification-templates']
   mutation: publish                              → invalidation مزدوج + إشعار نجاح بالـ version
   channel: postgres_changes(notification_templates) → invalidate (إشارة لا محتوى)
   صراع القفل (MAIL01/TPL… ) → dialog: [تحديث اللقطة] [نسخ لقطة] [استبدال قسري ← يتطلب صلاحية + إعادة تأكيد]
```

قواعد: لا `staleTime: 0` على جداول الإعدادات (إهدار + وميض)؛ لا `enabled` بلا بوابات صلاحية (تسريب مجهول)؛ كل استعلام محمي بـ `can_*` مستعلام مسبقاً؛ والمحرّر يُقفل `readOnly` (لا يُخفى) لغير الحامل — **السلوك نفسه المُعتمَد في شاشة الأدوار**.

## 4. المخطط المنطقي الكامل (Logical Flow) — من الحفظ إلى الإيميل

```
(1) التهيئة (مرة واحدة لكل بيئة)
   admin UI ──► admin_update_email_transport(host, port, sender_name, username, tls, …)
        │        │
        │        ├─ 42501/22023 gate + optimistic lock
        │        └─ upsert notification_transports ──► audit(settings.updated) ──► commit
        │
   admin UI ──► admin_set_email_password(pw)
        │        ├─ (A) pgsodium.crypto_secretbox(pw_bytes, nonce, vault.decrypted_secrets(key_id))
        │        ├─ (B) worker-side AES-GCM(pw, DEK) + wrapped DEK  ←  المخطط نفسه
        │        └─ insert/update notification_transport_secrets(bytea…) ──► audit(عنوان + بصمة 8)
        └─ لا نص صريح في القاعدة · لا نص في الذاكرة بعد المعاملة · لا نص في السجلات

(2) تحرير القالب
   Editor ──► validate locally ──► admin_upsert_notification_template_draft
        │      └─ tokenizer validation (unknown token / html allowlist / reserved names)
        ▼
   Preview ──► admin_render_notification(key, locale, sample_variables, mode='preview')
        │        └─ 1) load active|draft  2) tokenize  3) type-check vars  4) escape-contextual
        │           5) assemble multipart  6) sha256 → content_hash
        ▼
   iframe sandbox (CSP, no network) — ما يراه المدير == ما سيُرسل (تطابق مفروض بالاختبار A10)

(3) النشر
   admin_publish_notification_template(key, locale, version, expected) ──► active (old → archived) ──► audit

(4) الإرسال (وقت الحدث — خارج قاعدة البيانات)
   trigger source (worker/scheduler/webhook)
        └─► mail-gateway Edge Function
                ├─ service_role: read transport (+ secret bytea) + active template(key, recipient locale)
                ├─ decrypt (in-memory only) ──► provider adapter (smtp_generic | smtp_office365 | https_api)
                ├─ render (identical contract to §2.4) with real variables + signed action token
                ├─ send ──► log {ok|error_class, latency, content_hash, request_key(dedupe)}
                └─ on failure: retry per policy (same version ⇒ same bytes) ──► notification_deliveries (لاحقاً)
```

**ثلاث دوائر أمان تُغلق المخطط:** (أ) النص الصريح لا يغادر طبقة التنفيذ أبداً؛ (ب) كل كتابة في القاعدة عبر RPC مُدقَّقة واحدة لكل كيان؛ (ج) العرض والمعاينة والإرسال تتشارك **عقد renderer واحداً** مضموناً باختبار تطابق (A10 + فحص المرآة).

| «الترجمة الآلية للغات الناقصة»                                     | قالب غير مُراجَع = رسالة خطأ عمومية باسم عميلنا                                                                               |

## 7. قائمة تحقّق ما قبل الاعتماد / ما بعد الترحيل (Acceptance Gates)

**قبل تنفيذ الترحيل (تحقّق بيئة):**

1. هل `pgsodium` و`supabase_vault` متاحان ومُفعَّلان في المشروع المستهدف؟ (إن لم يكونا ⇒ D3=(ب) حتمياً لا اختيارياً).
2. هل `pgsodium.trusted_mode` مفعّل ومن هو القادر على تعطيله؟ هل `zeroize_secrets` مُهيّأ؟
3. هل منافذ `587/465/25` مسموحة بالصدور من طبقة التنفيذ (Supabase Functions/Edge)؟ ومن `docker` المحلي؟
4. هل `log_statement`/`log_min_duration_statement`/`pg_stat_statements` مُفعّلة في المشروع؟ (تُقَرّر حجم خطر T6 وتفرض عدم وضع أي مادة مفتاح في نص SQL).
5. هل `auth` يملك `anon` أي وصول لجدول الحالة (اختبار A1 **على المشروع الحيّ**، لا المحلي)؟

**عند كتابة الترحيل (عقد إلزامي — في المرحلة الثانية):** 6. `create extension if not exists pgsodium` داخل **schema مُخصَّص** (`with schema pgsodium`) كما تُوصي الأمانات المعتادة، و`grant` مقصور على الأدوار اللازمة. 7. كل جدول: `enable + force row level security` · `revoke all … from public, anon, authenticated` · منح انتقائي · **بلا سياسات كتابة**. 8. كل دالة: `security definer` + `set search_path = pg_catalog, public` + owner مُنخفض الصلاحيات + `revoke execute from public, anon` + `grant` انتقائي. 9. البذور بـ `on conflict do nothing` (لا تسحق تهيئة عميل قائم)، والقوالب الثلاثة بـ `version=1 · active · content_hash`. 10. `alter type public.audit_action add value if not exists …` في الذيل فقط، وكل استدعاء مُعرَّف بـ `::public.audit_action` (النمط القائم). 11. `alter publication supabase_realtime add table public.notification_templates` فقط (لا الأسرار). 12. trigger الحارس (منع تعديل المنشور + منع نص صريح في الأسرار) **قبل** السياسات في الترتيب المنطقي، ومُختبَر. 13. تحديث `scripts/audit/database.mjs` بكل حالات §3.7 وتمرير `npm run typecheck/lint/test` + CI أخضر قبل الدمج (بوابة CI الموجودة `supabase-migration.yml`). 14. `.env.example` يُحدَّث بـ `VITE_PUBLIC_APP_URL` إن لزم، **وصفراً** من المفاتيح السرية؛ وتوثيق `MAIL_MASTER_KEY` في runbook التشغيل لا في المستودع.

**مخرجات إضافية مقترحة للمرحلة الثانية (غير مطلوبة الآن):** runbook دوران المفتاح (3 خطوات: bump `key_version` → re-wrap → verify fingerprint)، runbook «الناقل مُعطَّل عمداً» (وضع الاختبار)، ومخطط ER مصغَّر يُلحق بالدراسة بعد الاعتماد.
