# قالب نظام الإدارة — Admin System Boilerplate

![Version](https://img.shields.io/badge/version-1.0.1-blue)

> تُقرأ نتائج الاختبارات والتدقيق من تشغيلات GitHub Actions الفعلية؛ لا تعرض هذه الصفحة شارات نجاح ثابتة أو أعداداً غير موثقة.

قالب متكامل جاهز للإنتاج (Production-Ready) يعتمد نموذج **التطوير السحابي بالكامل (Cloud-Only)**:
كل التحسينات تحدث على GitHub و Vercel و Supabase —
دون الحاجة لبيئة تطوير محلية.

## 🚀 البدء السريع (Getting Started)

- 📘 **[دليل إعادة استخدام القالب (Reuse Guide)](docs/runbooks/reuse-guide.md):** خطوات عملية لإطلاق مشروع جديد مستقل من الصفر (Supabase + Edge Functions + Vercel + CI/CD + تأمين المالك الأول) في أقل من 30 دقيقة.
- 🔐 **[دليل الإعداد الأولي وتأسيس المالك](docs/runbooks/initial-setup.md):** تفاصيل آلية أول تسجيل (`owner`) وحسابات QA والمشاريع القائمة.

## ✨ الميزات الرئيسية

- 🛡️ **أمان مؤسسي (Enterprise Security):** سياسات RLS صارمة وحماية أدوار `owner` و`super_admin` عبر Triggers، مع منع إسناد الأدوار المحمية عبر واجهات API العادية. أول تسجيل Auth في مشروع جديد يحصل على `owner` وكل الصلاحيات صراحةً داخل قاعدة البيانات.
- 🔑 **استعادة كلمة مرور باعتماد يدوي (Manual Approval):** تدفق «نسيت كلمة المرور» المؤقت عبر طلبات يراجعها المالك أو مدير النظام، بسبب قيود مزودي البريد المجانيين (مثل Resend Sandbox)؛ كود استعادة OTP الأصلي محفوظ كمرجع جاهز لإعادة التفعيل بعد ضبط SMTP حقيقي.
- 📧 **نظام إشعارات متكامل:** محرر قوالب آمن مع معاينة حية، ومنع تكرار الإرسال
  (Idempotency) على مستوى قاعدة البيانات — **دون إرسال بريد فعلي في الوضع الحالي**.

  > The template includes a **reference implementation** of SMTP transport (under
  > `src/lib/mail/`) that is not yet wired into a background worker. Password recovery
  > currently uses manual admin approval.

- 🔔 **إشعارات داخل التطبيق (In-App):** جرس تنبيهات في الشريط العلوي مع عدّاد غير المقروء وقائمة منسدلة، تعمل داخل الواجهة فقط دون بريد أو إشعارات هاتف أو أي خدمة خارجية.
- 📦 **قابلية إعادة الإنتاج (Reproducible):** ميزة تصدير واستيراد حزم الإشعارات (Bundle) لنقل الإعدادات بين المشاريع بضغطة زر دون تسريب الأسرار.
- ☁️ **تطوير سحابي بحت (Cloud-Only):** مصمم للعمل بالكامل عبر GitHub, Vercel, و Supabase Dashboard دون الحاجة لبيئة تطوير محلية معقدة.
- 🌍 **ثنائي اللغة ومتجاوب:** دعم كامل للعربية (RTL) والإنجليزية (LTR) مع تخطيط متجاوب ذكي (`@container`) يعمل بسلاسة على الهاتف والحاسب.

| الطبقة     | التقنية                                                  |
| ---------- | -------------------------------------------------------- |
| الواجهة    | Vite 8 + React 19 + TypeScript 6 (strict)                |
| الأنماط    | Tailwind CSS 4 (مظهر داكن/فاتح) + Lucide React           |
| اللغة      | ثنائية اللغة: العربية (RTL، افتراضي) + الإنجليزية (LTR)  |
| الخلفية    | Supabase (PostgreSQL) مع ترحيل تلقائي عبر GitHub Actions |
| المصادقة   | Supabase Auth (بريد/كلمة مرور) مع حماية المسارات         |
| الاختبارات | Vitest + Testing Library                                 |
| الاستضافة  | Vercel                                                   |

## ⚠️ قيود معروفة (Known Limitations)

قيود **مقصودة** في النسخة الحالية، موثّقة هنا حتى لا تُقرأ كمزايا جاهزة. كل بند مؤجَّل
كقضية مستقلة (العنوان بين علامتي اقتباس هو عنوان القضية).

| القيد                                      | الواقع في الكود                                                                                                                                                                                                                                                                             | الأثر والتتبع                                                                                                                                                               |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **الترقيم (Pagination)**                   | سقف ثابت بلا ترقيم خادومي: `USERS_MAX_ROWS = 1000` في `src/hooks/useUsersManagement.ts` مع `.range(0, USERS_MAX_ROWS - 1)` (وكذلك `REQUESTS_MAX_ROWS = 1000` لطابور إعادة التعيين، `MATRIX_MAX_ROWS = 5000` لمصفوفة الأدوار، `TICKETS_MAX_ROWS = 500` للتذاكر، `FEED_LIMIT = 20` للتنبيهات) | الصفوف بعد أول 1000 (مرتبة بـ `created_at` ثم `id`) لا تُجلب أبداً، والتصفية تعمل على المجلوب فقط (`filteredUsers`). مؤجَّل: «feat(users): add pagination beyond 1000 rows» |
| **تحديد المعدل (Rate limiting / CAPTCHA)** | «نسيت كلمة المرور» يُدرج صفاً في `password_reset_requests` بسياسة `for insert to anon, authenticated`؛ الحارس الوحيد هو الفهرس الجزئي الفريد `password_reset_requests_one_pending_per_email` (طلب واحد غير منتهٍ لكل بريد). لا CAPTCHA ولا تحديد معدل لكل عنوان IP في الواجهة               | الرد الموحّد يمنع استكشاف الحسابات، لكن الطابور الإداري يبقى قابلاً للإغراق. مؤجَّل: «feat(auth): add rate limiting / CAPTCHA to password reset requests»                   |
| **الاحتفاظ بـ `audit_logs`**               | لا توجد مهمة تنظيف لسجل التدقيق؛ مهمة `pg_cron` الوحيدة للاحتفاظ هي `prune-expired-user-notifications-daily-0315` (90 يوماً على `user_notifications`)                                                                                                                                       | السجل append-only (أدوار API بلا `insert/update/delete`) وينمو بلا حد؛ التنظيف مهمة مشغّل يدوية. مؤجَّل: «feat(audit): add retention policy for audit_logs»                 |
| **البريد الصادر (SMTP)**                   | `src/lib/mail/` تنفيذ **مرجعي** غير مستورد في الإنتاج ولا منشور كدالة خلفية                                                                                                                                                                                                                 | لا بريد معاملاتي؛ استعادة كلمة المرور باعتماد يدوي. مؤجَّل: «feat(email): wire SMTP worker for transactional email»                                                         |
| **استعادة OTP**                            | تدفق `src/lib/passwordRecovery.ts` وصفحة `/reset-password` باقيان كمرجع غير مستخدم                                                                                                                                                                                                          | الاستعادة الذاتية تحتاج SMTP حقيقياً أولاً. مؤجَّل: «feat(auth): implement OTP password recovery»                                                                           |

## مساحات العمل وضبط المشروع

مسارات مساحات العمل المعتمدة إنجليزية وثابتة: `/workspaces/aps` و`/workspaces/workshops-10th`
و`/workspaces/reports`، بينما تظهر أسماؤها العربية المترجمة وأيقوناتها في الواجهة وعنوان المستند.
المصدر الوحيد للكتالوج هو `src/lib/workspaces.ts`؛ لا يوجد سجل مساحات عمل مكرر في قاعدة البيانات.
الشاشات الحالية هياكل مهيأة فقط، ولا تتضمن وحدات قيود APS أو الورش أو التقارير الداخلية.

صفحة **ضبط المشروع** على `/settings/project` هي آخر عنصر ضمن «الضبط والتحكم»، وتتطلب الصلاحية
الصريحة `project.settings:manage`. تُمنح افتراضياً للدورين `owner` و`super_admin`؛ ولا تكفي عضوية
`admin` أو صلاحية `settings.manage` وحدها. تظهر للمستخدم غير المخوّل شاشة 403، ويرفض RPC المستقل
`admin_update_project_settings` الكتابة بـSQLSTATE `42501`. تحفظ الكتابة الناجحة حقول الهوية الستة
(بما فيها الشعار والأيقونة) وتضيف حدث `project.settings_updated` إلى `audit_logs` في المعاملة نفسها.
يبقى مسار الإعدادات العامة القديم و`admin_update_app_identity` ببوابتهما وامتيازاتهما دون تغيير.

## لوحة المؤشرات التنفيذية (Executive Dashboard)

الشاشة الرئيسية لمالك `dashboard:read` (‏`executive` و`admin` و`owner`/`super_admin` عبر `*`).
كل ما تراه يُقرأ من استدعاء واحد: `public.get_executive_dashboard(p_window_days int default 30)`.

**البطاقات الأربع:** إجمالي المستخدمين · بانتظار الاعتماد (مع مؤشر ثانوي صغير للموقوفين،
وليس بطاقة خامسة حتى لا يختلط مفهوما «معلّق» و«موقوف») · طلبات إعادة تعيين كلمة المرور
المعلّقة · سجّلوا الدخول اليوم. أسفلها: رسم أعمدة للتسجيلات اليومية (30 يوماً)، توزيع الأدوار،
وآخر 10 أحداث إدارية من `audit_logs`.

**قاعدة الوقت (توقيت المشروع):** تُحسب الإحصائيات بتوقيت المشروع المحفوظ في `app_settings`
(المفتاح `appearance.default_timezone`، وقيمته الافتراضية عند الزرع `Europe/Paris`، ويُكتب عبر
`admin_update_appearance_settings` مع تحقق IANA): «سجّلوا الدخول اليوم» يُحسب من
`auth.users.last_sign_in_at` ضمن اليوم التقويمي المحلي للمشروع، وفترة التسجيلات اليومية تُقسَّم
بالمنطقة نفسها، والحدود تُحسب كمنتصف ليل محلي فعلي فتبقى أيام التوقيت الصيفي دقيقة
(23/25 ساعة) في المناطق ذات التوقيت الصيفي. يقرأ الدال القيمة حياً في كل استدعاء فتتحرك
المؤشرات مع تغيير الإعداد مباشرة، وأي قيمة مفقودة أو تالفة تسقط إلى `UTC` ويظهر ذلك في الرد
حيث يعيد الدال حقل `timezone` بالمنطقة المُطبّقة فعلياً وتعرضها الواجهة بجانب «آخر تحديث»
وتُصيغ بها طوابع النشاط الأخير — لا يُستخدم توقيت المتصفح أبداً، فالرقم لا يتغير بتغيّر جهاز المشرف.

**ملاحظة:** العطلات الأسبوعية (إعداد `appearance.weekend_days`) هي أيام عطلة أسبوعية فقط،
وليست عطلات رسمية — العطلات الرسمية تحتاج نموذج بيانات منفصلاً ولا تُستنتج من إعداد عطلة الأسبوع.

**لماذا RPC واحد بدل استعلامات مباشرة؟** جداول المؤشرات محمية بـRLS يشترط `is_admin()`
أو أحد الأدوار المحمية. استعلام من المتصفح بحساب `executive` يعود بلا أخطاء لكنه يعرض أرقاماً
مقنّعة (صفّه الشخصي فقط) — وهي أسوأ من الخطأ لأنها تبدو معقولة. لذلك تُحسب كل التجميعات داخل
`SECURITY DEFINER` بوظيفة واحدة، ببوابة صلاحية صريحة و`search_path` مثبّت:

1. `auth.uid()` موجود و`is_active_user()` صحيح (الحساب نشط)، وإلا `42501`.
2. `has_permission('dashboard:read')` — وهي وحدها صلاحية `executive` — وإلا `42501`.
3. `p_window_days` بين 7 و90، وإلا `22023` (`invalid_window`).

`EXECUTE` مسحوب من `public` و`anon` ومسموح لـ`authenticated` و`service_role` فقط، والدالة
`stable` تقرأ ولا تكتب. شكل الرد تجميعي بحت: لا صفوف، لا بريد، لا كلمات مرور (`new_password`
لا يُنتقى أبداً)، و`audit_logs.metadata` لا يخرج خاماً — فقط اسم الحدث و`role_slugs`،
والأسماء تُستبدل ببريد مقنّع (`m***@example.com`) عند غياب الاسم الكامل.

**الواجهة:** `useExecutiveDashboard` (TanStack Query) يخزّن النتيجة 60 ثانية ويعيد الجلب كل
60 ثانية وعند عودة التركيز، ويتوقف تماماً (`enabled: false`) إن لم يملك الحساب الصلاحية.
الحالات الأربع صريحة: هيكل تحميل، لوحة خطأ مترجمة مع زر إعادة محاولة (رسالة «غير متاح» تظهر
أيضاً لو لم يُطبَّق الترحيل بعد، بدل شاشة بيضاء)، حالة فراغ، ثم البيانات. الفشل لا يُرسم أبداً
كأصفار: `—` يعني «غير معروف» و`0` يعني صفراً حقيقياً.

**ملاحظة عن التوزيع:** المستخدم قد يحمل أكثر من دور، لذا مجموع أشرطة الأدوار قد يتجاوز إجمالي
المستخدمين؛ الحاشية تقول ذلك صراحةً بدل ادّعاء أن الأشرطة تشكّل كلاً واحداً. من لا دور له يظهر
في صف «بلا دور».

**الاختبارات:** `scripts/audit/database.mjs` يثبت أن `anon` و`viewer` يُرفضان بـ42501، وأن
`executive` يرى الشكل الكامل مع 30 نقطة يومية صفرية التعبئة، وأن حساباً موقوفاً يفقد الوصول،
وأن حقن `new_password`/بريد خام في `metadata` لا يظهر في الرد، وأن `admin` يحمل الصلاحية
دون `viewer`. على جهة الواجهة: اختبارات البوابة (`isDashboardOnlyActor`)، والهوك، والمكوّنات،
والصفحة (تحميل/خطأ/فراغ/عدم صلاحية).

## اعتماد المستخدمين الجدد

أول حساب Auth على مشروع جديد يحصل على `owner` معتمد تلقائيًا ويؤكَّد بريده ذريًا. الترحيل
`20261017000000_add_user_approval_workflow.sql` يعتمد الحسابات الموجودة مسبقًا مرة واحدة؛
التسجيلات التالية تكون `pending` بلا دور أو تأكيد بريد تلقائي. لا تُفتح البيانات حتى الاعتماد؛
سياسات RLS تتيح للحساب المعلّق قراءة ملفه الشخصي فقط، وتمنع تحديث `approval_status`
مباشرةً من `authenticated`. بعد الاعتماد يمنح النظام `viewer` ويؤكّد البريد.

مثال: افتح **الإعدادات ← المستخدمون ← المستخدمون المعلقون** بحساب `owner` أو
`super_admin` ثم اختر «اعتماد» أو «رفض». يمكن أيضًا منح القدرة المحددة
`users.approve` لمستخدم آخر؛ يرى هذا المفوّض طابور الاعتماد فقط ويستطيع منح دور
`viewer` لا غير. تُستدعى Edge Function `approve-user` بجلسة المسؤول؛ تتحقق من JWT ثم
تستدعي RPC بمفتاح الخدمة على الخادم فقط. انشر الدالة مع الترحيل
(`supabase functions deploy approve-user`) ولا تضع مفتاح الخدمة في المتصفح.
عملية الاعتماد/الرفض تُسجل في `audit_logs` كـ `user.updated` مع اسم الحدث
`user.approval_approve` أو `user.approval_reject` في `metadata.event` (حقل action
من نوع enum). لا يمكن لـ authenticated استدعاء RPC مباشرةً.

> ملاحظة: إذا كان Supabase Auth يشترط تأكيد البريد قبل تسجيل الدخول، فقد تعيد Auth
> رسالة «البريد غير مؤكد» للحساب المعلّق أو المرفوض قبل أن تتمكن الواجهة من قراءة
> حالة الاعتماد. يظل RLS يمنع الوصول؛ يمكن للمسؤول رؤية الحالة من صفحة الإدارة.

## Admin User Management Tools (أدوات إدارة المستخدمين)

أداتان للمالك ومدير النظام (`owner` / `super_admin` فقط — القرار D2)، كلتاهما في
**الإعدادات ← المستخدمون**:

| الأداة                      | ماذا تفعل                               | كلمة المرور                             |
| --------------------------- | --------------------------------------- | --------------------------------------- |
| **إضافة مستخدم**            | تنشئ حساب Auth جديداً بريداً تختاره أنت | تُولَّد وتُعرض **مرة واحدة** على الشاشة |
| **إعادة تعيين كلمة المرور** | تستبدل كلمة مرور حساب **قائم**          | تُولَّد وتُعرض **مرة واحدة** على الشاشة |

### الفرق بين الدعوة والمسار الآلي

يوجد في النظام مساران لإنشاء/استعادة كلمة مرور، وهما **مقصودان ومختلفان**:

**١. الدعوة المباشرة (هذه الأدوات).** المسؤول يختار البريد، والخادم ينشئ الحساب عبر
`auth.admin.createUser` ثم يعرض كلمة مرور مؤقتة على الشاشة. لا بريد يُرسل ولا رابط ولا
رمز OTP — الحساب جاهز للاستخدام فوراً بكلمة المرور المعروضة. مناسب عندما يكون المسؤول
قادرًا على تسليم الكلمة عبر قناة آمنة.

**٢. طلب الاستعادة اليدوي.** المستخدم يرسل بريده فقط. عند الاعتماد، يولّد النظام كلمة مرور عشوائية مؤقتة تُعرض مرة واحدة في نافذة `PasswordRevealDialog`، ولا تُخزّن في قاعدة البيانات. يمكن منح `password_reset.manage` للوصول إلى الطابور الآمن، بينما
يبقى التنفيذ معتمدًا على Edge Function تتحقق من JWT والصلاحية. راجع قسم
_Password Recovery_ أدناه.

> لا تستبدل إحدى الأداتين الأخرى: `admin-invite-user` هي الوحيدة التي تستدعي
> `createUser` (ولذلك وحدها يمكن أن تصطدم ببريد مسجَّل)، و`admin-reset-password` هي
> الوحيدة التي تعمل على صف طلب معلّق. الاثنتان تستدعيان `auth.admin.updateUserById`
> لسببين مختلفين؛ لا تدمجهما.

### كلمة المرور المؤقتة

- **١٦ حرفاً** من `A-Za-z0-9`، **بدون الرموز الملتبسة** `0 1 O o I l` (القرار D4) —
  كي تنجو الكلمة من قراءتها هاتفياً أو إعادة كتابتها من لقطة شاشة.
- **تُعرض مرة واحدة ولا تُخزَّن في أي مكان** (القرار D1): لا جدول، لا `metadata` في
  `audit_logs`، لا سطر سجل. المكوّن `PasswordRevealDialog` مشترك بين التدفقين.
- **لا يوجد علم «إجباري التغيير»** (القرار D3)؛ يكفي التنبيه المعروض في الحوار بأن
  يُنصح المستخدم بتغييرها بعد أول دخول.

### الحماية والتدقيق

- **حماية المالك الأصلي** (القرار D6): لا يمكن دعوة المالك الأصلي ولا إعادة تعيين كلمة
  مروره. تُفرض في SQL عبر `is_original_owner()` لا في الواجهة فقط.
- **قائمة الأدوار** المسموح منحها بالدعوة: `viewer` / `editor` / `admin` / `executive`
  (القرار D5). `owner` وأي دور `is_super_admin` مرفوضة دائماً.
- **سجل التدقيق:** `user.invited` و`user.password_reset_by_admin` في `metadata.event`
  (لأن `audit_action` من نوع enum). لا تحمل سجلات التدقيق أي مادة سرّية.
- **RPCs الثلاثة** (`admin_invite_user`, `admin_verify_password_reset_authority`,
  `admin_record_password_reset`) من نوع `SECURITY DEFINER` مع `search_path` مثبّت،
  و`EXECUTE` ممنوح لـ `service_role` وحدها — فـ `anon` و`authenticated` لا يصلان إلى
  جسم الدالة أصلاً.

> **ترتيب المراحل مقصود:** البوابة (تحقق بلا كتابة) ← الكتابة في GoTrue ← سجل التدقيق.
> إذا فشل السجل بعد نجاح الكتابة، تبقى كلمة المرور معروضة (حساب بلا كلمة مرور يعرفها
> أحد أسوأ من سطر تدقيق ناقص) مع تحذير `auditRecorded: false` بجانبها.

انشر الدالتين مع الترحيل:

```bash
supabase functions deploy admin-invite-user
supabase functions deploy admin-set-password
```

## الإشعارات داخل التطبيق (In-App Notifications)

جرس تنبيهات في الشريط العلوي (`Topbar`) مع عدّاد غير المقروء وقائمة منسدلة، تعرض أحداثاً
مثل «لديك طلب اعتماد جديد» و«طلب إعادة تعيين كلمة مرور». **للإشعارات دورة حياة؛ تُحلّ تلقائياً عند إتمام الإجراء.** **النظام داخلي بالكامل:** لا بريد
إلكتروني، لا إشعارات هاتف، ولا أي خدمة خارجية — ولا يتقاطع مع جداول `notification_*` الخاصة
بالبريد (SMTP والقوالب) ولا مع `audit_logs`.

الترحيل: `20261022000000_in_app_notifications.sql`.

| العنصر    | التفصيل                                                                                                        |
| --------- | -------------------------------------------------------------------------------------------------------------- |
| الجدول    | `public.user_notifications` — سُمّي كذلك تفادياً للتداخل مع `notification_*` (البريد)                          |
| المحتوى   | **مفاتيح i18n + params**، لا نصوص منجَّزة: `title_key`/`body_key` مثل `notifications.type.user_approved.title` |
| الخصوصية  | معرّفات المستهدفين مقنَّعة (`p***@example.invalid`) بنفس نمط تعقيم `audit_logs`                                |
| RLS       | `enable` + `force`؛ السياسة الوحيدة `user_id = auth.uid()` — كل مستخدم يرى إشعاراته فقط                        |
| الكتابة   | لا INSERT/UPDATE/DELETE من المتصفح؛ التعديل فقط عبر RPCs بـ`security definer`                                  |
| البث الحي | منشور في `supabase_realtime` بهوية PK فقط؛ الإشارة تُبطل الكاش ولا تُقرأ حمولتها                               |
| الاحتفاظ  | 90 يوماً عبر مهمة `prune-expired-user-notifications-daily-0315`                                                |

### مبدأان معماريان مهمان

**١. فشل الإشعار لا يُفشل العملية الأصلية.** كل دالة Trigger تعزل عملها في كتلة `exception`
وتتدهور إلى `WARNING`. خسارة إشعار مقبولة؛ خسارة اعتماد مستخدم ليست كذلك. هذا مُختبَر في
`scripts/audit/database.mjs` بتعطيل مساعد الإشعارات كلياً والتحقق من بقاء العمليات الثلاث ناجحة.

**٢. نقطة مركزية لتحديد المستلِمين بالصلاحية الفعلية.** تحديد المستلِمين معزول في
`public.resolve_notification_recipients(p_type, p_subject_id)`، ويعتمد على
`public.user_has_permission` (`users.approve` و`password_reset.manage`) ليشمل المالكين
ومديري النظام والمفوّضين الفعليين بالصلاحية على السواء.

### الواجهة والآلية

- `NotificationBell` + `NotificationDropdown` في `src/components/layout/` — يعيدان استخدام عقد
  قائمة الحساب حرفياً (إغلاق بالنقر خارجها، `Escape` مع إرجاع التركيز، إغلاق عند تغيّر المسار).
- `useUserNotifications`: **استعلامان منفصلان** — عدّاد غير المقروء (`head: true` بلا صفوف)
  والقائمة — مع تحديث متفائل واسترجاع عند الفشل.
- `useUserNotificationsRealtime`: هجين — Realtime كإشارة إبطال (مفلترة بـ`user_id=eq.<uid>`)
  مع تجميع 250ms، ويلجأ إلى polling كل 30 ثانية عند `offline` فقط.
- **الجرس يظهر لكل الحسابات** بما فيها المعلّقة وذات لوحة التحكم فقط: الحساب المعلّق يملك
  مجموعة صلاحيات فارغة، وهو بالضبط من يجب أن يرى «تم اعتماد حسابك». لذا البوابة هي الملكية
  (RLS) لا الصلاحية.

> تنبيه على الأسماء: `useNotificationRealtime` (بدون `User`) موجود أصلاً ويتبع محرر قوالب
> البريد. الـhook الجديد سُمّي `useUserNotificationsRealtime` ولا يشاركه اسم القناة.

## حماية المالك الأصلي

ترحيل **`20261017010000_protect_original_owner.sql`** (ترحيل جديد بعد ترحيل الاعتماد
المنشور؛ لا يُعدَّل ملف الترحيل القديم) يجعل إسناد `owner` وملف حسابه وهوية Auth
ودوره وصلاحياته غير قابلة للإزالة أو الاستبدال عبر التطبيق. تمنع سياسات RLS
تعديل/حذف إسناد الدور للمستخدم المصادق؛ وتمنع Triggers أيضًا التعديل المباشر
بالـ SQL وعمليات `service_role` والتحديثات عبر دوال `SECURITY DEFINER`، بما في
ذلك حذف `auth.users` المتسلسل أو تعليق المالك أو تغيير حالة اعتماده. ترفض دوال
`admin_set_user_roles` و`admin_set_user_status` و`admin_approve_user` استهدافه
صراحةً. شارة «محمي» ورسالة المالك التفصيلية في الواجهة طبقة إرشادية فقط،
والقاعدة هي حاجز الأمان الفعلي.

الرفض يطلق خطأ `42501` ويُكتب في **سجل PostgreSQL** باستخدام `RAISE LOG`؛
لا يمكن حفظ حدث الرفض في `audit_logs` داخل نفس المعاملة التي تُلغى بالخطأ
(سيُلغى إدراج التدقيق معها). يجب ربط سجل قاعدة البيانات بتجميع السجلات
لتتبع المحاولات المرفوضة. عمليات الموافقة/الرفض الناجحة تُحفظ في `audit_logs`
كما سبق. يظل مشرف PostgreSQL المتميز قادرًا على تعطيل Triggers أو تغيير المخطط؛
هذه صلاحية تشغيلية خارج حدود حماية أدوار التطبيق وتتطلب ضوابط مؤسسية منفصلة.

## الإعداد الأولي

لا يحتوي القالب حسابًا افتراضيًا أو كلمة مرور bootstrap. بعد تطبيق migrations على مشروع Supabase جديد، سجّل **المالك المقصود أولاً** من خيار إنشاء الحساب في `/login`. يتحقق trigger ذري من أن `auth.users` كان فارغًا قبل الإدراج، ويؤكد بريد هذا التسجيل ويمنحه `owner` مع كل صلاحية صراحةً. كل تسجيل لاحق يحصل على `pending` بلا دور حتى يعتمد المالك أو مدير النظام طلبه، حتى لو أرسل `user_metadata` يحاول طلب دور `owner` أو `super_admin`. لا توجد RPC عامة تمنح أي دور محمي.

ترتيب التسجيل وحده لا يثبت ملكية الحساب. أبقِ التسجيل محصورًا بالمالك المقصود حتى يكمل أول تسجيل، ولا تفتح التسجيل العام قبله. بعد ذلك يمكن للمسؤول إدارة حسابات المستخدمين المعتادة. للمشاريع القائمة التي لديها مستخدمون Auth قبل الترحيل، لا يُرقّى تسجيل جديد تلقائيًا؛ راجع [دليل الإعداد](docs/runbooks/initial-setup.md) قبل المتابعة.

للتطوير المحلي: شغّل `supabase start` ثم `supabase db reset`، واضبط `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY`، ثم افتح `/login` وأنشئ أول مستخدم محلي. لا يحتاج التسجيل إلى GitHub secrets أو مفتاح `service_role`.

> 🔒 لا تضع كلمات مرور أو مفاتيح خدمة في المستودع. تدفق التطبيق لا يقرأ بيانات اعتماد مخزنة، ولا يستنتج الدور من `user_metadata`.

### الأدوار والصلاحيات

- **`owner` — المالك الأصلي:** أول مستخدم Auth في مشروع جديد؛ دور محمي ويحصل صراحةً على كل صف في `permissions`، بما فيه `*`. ينقل الترحيل أول إسناد حالي لـ `super_admin` إلى `owner` إن وُجد.
- **`super_admin` — مدير النظام المحمي:** يبقى دورًا محميًا كما كان، مع إسناد `*` ومصفوفة صلاحياته الأصلية دون تغيير. لذلك يظل `*` يمنحه فعليًا كل القدرات؛ الفرق أن `owner` هو دور التأسيس ويمتلك أيضًا كل صلاحية فردية صراحةً.
- **`admin` — مدير:** مجموعة الصلاحيات الإدارية المحددة في مصفوفة RBAC، دون علامة الدور المحمي.
- **`editor` — محرر:** صلاحيات لوحة المعلومات ومساحات العمل المحددة له.
- **`executive` — الإدارة العليا:** صلاحية واحدة فقط `dashboard:read`، بلا أي وصول إداري آخر؛
  وجودها وحده يجعل الهيكل «لوحة فقط». أي صلاحية تشغيلية إضافية تُخرجه من هذا الوضع.
- **`viewer` — مشاهد:** الاطلاع على لوحة المعلومات فقط (`dashboard.view`، لا يقرأ مؤشرات
  لوحة المؤشرات التنفيذية).

الدوران `owner` و`super_admin` محميان من التعديل والإسناد عبر واجهات API العادية، ولا توجد RPC عامة لمنحهما. لم تُسحب صلاحية `*` التاريخية من `super_admin` في هذا التغيير حفاظًا على التوافق.

### الدور مقابل القدرة المفوّضة

الدور (`role`) هو حزمة صلاحيات دائمة نسبيًا تُدار عبر RBAC؛ أما القدرة (`capability`)
فهي استثناء محدود لمستخدم بعينه ومخزّن في `user_capabilities` مع مانحها ووقت المنح
وانتهاء اختياري وسجل سحب. تُدمج القدرات غير المنتهية مع صلاحيات الدور في
`has_permission()` و`get_my_capabilities()` فقط عندما يكون الحساب نشطًا ومعتمدًا.

لا يستطيع منح القدرات أو سحبها إلا `owner` و`super_admin`، ونطاق ما يمكن تفويضه
يحدّده المالك نفسه كما في القسم التالي (الافتراضي: `users.approve` و`password_reset.manage`).
يمنع الخادم منحها للنفس أو منح `*` أو
`roles.manage`، ولا تُمنح تلقائيًا للأدوار الإدارية العادية. لا تحوّل القدرة صاحبها
إلى `admin`: `is_admin()` ما زالت تعتمد على `*` الموروثة من الأدوار وحدها. مفوّض
`users.approve` يرى طابور الطلبات المعلّقة فقط ويعتمدهم بدور `viewer`؛ ومفوّض
`password_reset.manage` يقرأ الـView الآمنة لطابور كلمات المرور ويعالج الطلبات عبر
الخادم، دون وصول إلى الجدول الخام.
إشعارات «طلب اعتماد مستخدم» و«طلب إعادة تعيين كلمة مرور» تصل إلى **كل من يملك
الصلاحية فعليًا** (`users.approve` / `password_reset.manage` عبر
`resolve_notification_recipients` → `user_has_permission`) — مالكًا كان أو
مفوّضًا — وليس إلى أدوار `owner`/`super_admin` فقط
(`20261102000000_fix_password_reset_notification_recipients.sql`).

### التفويض الحُبَيبي للصلاحيات (Granular Capability Delegation)

أيّ الصلاحيات يجوز تفويضها لمستخدم فردي لم يعد قرارًا مكتوبًا في الكود، بل سياسة
يتحكم بها المالك من الواجهة (`20261030000000_permission_delegatable.sql`):

- **المصدر الوحيد للحقيقة:** العمود `permissions.is_delegatable`. زُرع مفعّلًا
  لصلاحيتين فقط — `users.approve` و`password_reset.manage` — وهما القائمة التي
  كانت ثابتة تاريخيًا، فلا يتغير أي سلوك حتى يختار المالك إضافة غيرهما.
- **من يتحكم:** `owner`/`super_admin` من قسم «تفويض الصلاحيات» في صفحة
  «الأدوار والصلاحيات» (تبديل فوري لكل صلاحية). الكتابة تمر حصريًا عبر
  `admin_set_permission_delegatable(p_permission_slug, p_is_delegatable, p_executor_id)`
  الذي يتحقق من دور المنفّذ ويربطه بـ`auth.uid()` في نداءات المتصفح، ويسجّل كل
  تغيير فعلي في `audit_logs` (حدث `permission.delegatable_updated` مع القيمتين
  السابقة والجديدة). إعادة تأكيد الحالة نفسها نجاح هادئ دون سجل إضافي.
- **الصلاحيات المحمية:** `*` و`roles.manage` **لا يمكن جعلهما قابلتين للتفويض
  أبدًا**. يحرس ذلك trigger (`permissions_guard_delegatable`) يرفض
  `is_delegatable = true` لهما على أي مسار كتابة — RPC أو جدول أو SQL مباشر،
  دون أي استثناء لسياق موثوق — وترفضهما الـRPC صراحةً (`permission_is_protected`)،
  وتتجاهلهما `get_my_capabilities()` داخل المنح أصلًا (دفاع متعدد الطبقات).
  في الواجهة تظهران بشارة «محمي» بدل مفتاح التبديل. النتيجة: التفويض لا يستطيع
  بنيويًا صناعة مدير.
- The owner role cannot be granted to additional users via any UI or API. It is
  exclusively assigned by the bootstrap flow.
- **نقطة الإنفاذ:** لحظة المنح. `admin_grant_capability` يقرأ العلم (مع قفل
  `FOR SHARE` حتى لا يسبق منحٌ تعطيلَ المالك) ويرفض غير المفعّل بخطأ
  `capability_not_delegatable` الذي يصل إلى حوار التفويضات برسالة واضحة. حوار
  «إدارة التفويضات» يعرض ديناميكيًا ما هو `is_delegatable = true` فقط، مع حالة
  فارغة صريحة عند عدم تفعيل أي صلاحية.
- **أثر التعطيل:** إيقاف صلاحية يمنع أي منح جديد فورًا، لكنه **لا يسحب بأثر رجعي**
  التفويضات السارية؛ هذه تنتهي بالسحب الصريح (`admin_revoke_capability`) أو بانقضاء
  تاريخها. إن احتجت إيقاف قدرة مفوّضة حالًا، اسحب المنح نفسه — تبديل العلم مفتاح
  سياسة للمستقبل، لا زر إيقاف طارئ للماضي.
- Visual Distinction: Delegated users are highlighted with a Shield badge in the Users Management table, and can be filtered using the 'Delegated' tab.
- Delegated users display a Clock icon with a color-coded badge (green/yellow/red) showing time until soonest delegation expiry. Permanent delegations show an Infinity icon.

## Edge Functions Deployment Guide (دليل نشر الدوال الخلفية)

### لماذا هذا مهم؟

Edge Functions هي دوال تعمل على **خوادم Supabase** (Deno Runtime)، لا في المتصفح ولا في
Vercel. وجودها في `supabase/functions/` داخل المستودع **لا يعني أنها تعمل** — فهي لا
تُنشر تلقائياً مع الكود، ولا يبنيها `npm run build`، ولا ينشرها Vercel.

**بدون نشرها، أي ميزة تعتمد عليها تفشل برسالة عامة:**

```
حدث خطأ غير متوقع، حاول مرة أخرى.
```

السبب أن الواجهة تستدعي `client.functions.invoke('<name>')`، فإذا لم تكن الدالة منشورة
عادت استجابة بلا جسم `{ error: '<code>' }` — والتصنيف في الـhook يسقط أي رمز غير معروف
إلى `unknown`، ومفتاحه `users.error.unknown`. أي أن **الرسالة العامة هي عَرَض لنشر
ناقص، لا خطأ في الكود**. عند ظهورها في ميزة تعمل عبر Edge Function، تحقّق من النشر
أولاً قبل البحث في المنطق.

> الدوال تعمل بمفتاح `service_role` على الخادم فقط. لا تضع المفتاح في المتصفح ولا في
> متغيرات `VITE_*`؛ الدوال تقرأه من بيئة Supabase نفسها.

### الدوال المطلوبة

| الدالة                    | الوظيفة                             | الميزة المرتبطة          |
| ------------------------- | ----------------------------------- | ------------------------ |
| `approve-user`            | اعتماد/رفض المستخدمين               | `users.approve`          |
| `admin-reset-password`    | تنفيذ طلبات إعادة تعيين كلمة المرور | `password_reset.manage`  |
| `admin-user-capabilities` | طابور اعتماد محدود وإدارة التفويضات | Capability delegation    |
| `admin-invite-user`       | دعوة مستخدم جديد                    | Owner / super_admin only |
| `admin-set-password`      | تغيير كلمة مرور مستخدم              | Owner / super_admin only |

> ✅ **الدوال الخمس تُنشر تلقائياً** عند الدفع إلى `main`: وظيفة `deploy_production` في
> `.github/workflows/supabase-migration.yml` تنشرها بعد `db push`. وخطوة
> `Assert every Edge Function has a deploy step` في وظيفة الاختبار تُفشل أي Pull Request
> يضيف دالة إلى `supabase/functions/` دون إضافة خطوة نشر لها — فلا يتكرر وصول ميزة
> إلى `main` بدالة غير منشورة.
>
> **النشر اليدوي أدناه يلزم في حالتين:** الإعداد الأول لمشروع جديد قبل أول دفع إلى
> `main`، وأي بيئة لا تنشرها الأتمتة (مشروع Preview أو Staging مثلاً).

### خطوات النشر (مفصلة)

```bash
# 1. دفع الترحيلات (مرة واحدة)
#    يجب أن تسبق نشر الدوال: الدوال تستدعي RPCs وجداول تنشئها الترحيلات،
#    ونشر دالة قبل وجود ما تستدعيه يتركها تفشل عند أول استدعاء.
supabase db push

# 2. نشر جميع الدوال (IDEMPOTENT، آمن للتكرار)
supabase functions deploy approve-user
supabase functions deploy admin-reset-password
supabase functions deploy admin-user-capabilities
supabase functions deploy admin-invite-user
supabase functions deploy admin-set-password

# 3. التحقق من أن الخمس أصبحت منشورة
supabase functions list
```

> `supabase functions deploy` **idempotent**: إعادة تشغيله تستبدل النسخة المنشورة ولا
> يضرّ تكراره. إن شككت في حالة النشر، أعد تشغيل أوامر النشر الخمسة.

> لنشر كل الدوال دفعة واحدة بلا أسماء: `supabase functions deploy` (بلا وسيط). لكن
> التصريح بالأسماء أوضح في السجلات ويمنع نشر دالة تجريبية عن طريق الخطأ.

### التحقق بعد النشر

من Dashboard → **Edge Functions** يجب أن تظهر الدوال الخمس بحالة **Active**. ثم
اختبر الميزة من الواجهة:

| الميزة                            | المسار                                   | الدالة المستدعاة                           |
| --------------------------------- | ---------------------------------------- | ------------------------------------------ |

| تنفيذ طلب إعادة تعيين كلمة مرور   | الإعدادات ← طلبات إعادة التعيين          | `admin-reset-password`                     |

## اختبارات E2E (Playwright)

تختبر مجموعة E2E المسارات الحرجة داخل Chromium حقيقي، مقابل **Supabase Local Stack مؤقت**؛ لا تستخدم مشروع Cloud ولا أسرار الإنتاج. ينشئ الإعداد مالكاً أولاً (للتحقق من bootstrap الفعلي)، ثم حساباً معلقاً وحساباً معتمداً ومستخدماً مفوّضاً بصلاحيتي الاعتماد وإدارة طابور الاستعادة. تُكتب كلمات المرور وحالة الجلسة مؤقتاً داخل `.auth/`، وهو مستثنى من Git ويُنظَّف بعد انتهاء التشغيل. لا تُضاف حسابات إلى `supabase/seed.sql`.

المتطلبات المحلية: Node.js بالإصدار المحدد في `.nvmrc`، وDocker يعمل، وSupabase CLI بالإصدار المستخدم في Actions. شغّل من جذر المستودع في Bash:

```bash
supabase start
supabase db reset --local

eval "$(supabase status --output env)"
export SUPABASE_URL="$API_URL"
export SUPABASE_ANON_KEY="$ANON_KEY"
export SUPABASE_SERVICE_ROLE_KEY="$SERVICE_ROLE_KEY"
export VITE_SUPABASE_URL="$API_URL"
export VITE_SUPABASE_ANON_KEY="$ANON_KEY"

functions_env="$(mktemp)"
printf 'SUPABASE_URL=%s\nSUPABASE_ANON_KEY=%s\nSUPABASE_SERVICE_ROLE_KEY=%s\n' \
  "$API_URL" "$ANON_KEY" "$SERVICE_ROLE_KEY" > "$functions_env"
supabase functions serve --env-file "$functions_env" > /tmp/admin-system-e2e-functions.log 2>&1 &
functions_pid=$!
trap 'kill "$functions_pid" 2>/dev/null || true; rm -f "$functions_env"' EXIT

npx playwright install chromium  # مرة واحدة لكل بيئة
npm run test:e2e
```

`playwright.config.ts` يشغّل Vite تلقائياً على `http://127.0.0.1:5173`؛ يمكن تغيير عنوان المتصفح عبر `E2E_BASE_URL`. للاستخدام التفاعلي: `npm run test:e2e:headed` أو `npm run test:e2e:ui`. يجب أن تكون قاعدة Auth المحلية فارغة قبل الاختبار كي يحصل أول مستخدم على دور المالك؛ نفّذ `supabase db reset --local` قبل كل تشغيل جديد.

تغطي المجموعة تسجيل الدخول الصحيح والخاطئ ورفض الحساب المعلق، دعوة مستخدم وكشف كلمة المرور المؤقتة، اعتماد حساب معلق، فتح جرس التنبيهات وإثبات وصول إشعار جديد عبر Realtime إلى الشارة، وتعيين كلمة مرور إدارية جديدة ثم نجاح تسجيل الدخول بها. كما تختبر مسارات المستخدم المفوّض: عزل طابور الاعتماد، اعتماد الحساب المعلق وحصر دوره في `viewer`، غياب إجراءات إدارة المستخدمين المحمية، قراءة طابور الاستعادة الآمن وبدء الاعتماد دون حقول كلمة مرور يدوية، رفض الطلب دون كلمة مرور، واعتماد الطلب بتوليد كلمة مرور مؤقتة عشوائية عبر GoTrue وكشفها مرة واحدة في `PasswordRevealDialog` ثم تسجيل الدخول بها.

يعمل `.github/workflows/e2e.yml` على طلبات PR إلى `main` أو يدوياً، ويشغّل Docker وSupabase المحلي وEdge Functions وChromium، ويرفع آثار Playwright عند الفشل فقط. بعد نجاح التشغيل الكامل على PR، صار فشل E2E يفشل الـWorkflow بدلاً من تجاهله. لجعله شرط دمج إلزامياً على `main`، أضف فحص الحالة `Chromium against local Supabase` إلى Required status checks في Branch Protection.

## المصادقة الحقيقية

- `src/lib/supabase.ts` ينشئ عميلاً كسولاً؛ بدون متغيرات بيئة يعيد `null` وتعرض شاشة
  الدخول **تنبيهاً واضحاً** بدل الانهيار.
- `AuthContext` يتابع الجلسة (`getSession` + `onAuthStateChange`) ويوفر التسجيل والدخول والخروج. أخطاء المصادقة تُطبّع وتُترجم عبر `AUTH_ERROR_KEYS`; الدور لا يُستمد من metadata.
- `RequireAuth` يعرض قائمة انتظار أثناء تحميل الجلسة ثم يوجّه الزائر إلى `/login`
  مع تذكّر المسار المطلوب (`location.state.from`).

### تغيير واستعادة كلمة المرور

- **سياسة واحدة** في `src/lib/validatePassword.ts`: ثمانية أحرف على الأقل فقط —
  لا رموز ولا أحرف كبيرة ولا قيود على المحارف، والمستخدم حر في اختيارها.
  ترجع `{ valid, errors }` ومفاتيح الترجمة لكل انتهاك، وكل النماذج تستخدمها.
- **تغيير كلمة المرور** في `/profile` (من قائمة الحساب): الحالية اختيارية
  للتحقق عبر Supabase، ثم الجديدة والتأكيد، والنجاح يمسح الحقول فوراً.
- **نسيت كلمة المرور** من شاشة الدخول: **طلب اعتماد يدوي** في الخطوة الحالية —
  البريد فقط ← صف `pending_approval` في `password_reset_requests` ← رسالة موحّدة.
  عند الاعتماد تُولَّد كلمة مرور عشوائية مؤقتة في Edge Function
  `admin-reset-password` وتُرسل إلى `supabase.auth.admin.updateUserById` دون
  تخزينها في DB، ثم تُعرض مرة واحدة في `PasswordRevealDialog` للنسخ.
  يمكن منح `password_reset.manage` للمفوّض لقراءة الطابور الآمن وتنفيذ الطلب.
- تدفق **OTP** السابق (البريد ← رمز من 6 أرقام ← كلمة مرور جديدة) وصفحة
  **`/reset-password`** باقية في الكود **كمرجع للمستقبل** حتى يُضبط SMTP حقيقي؛
  الواجهة الحالية لا تستدعيهما.

كل التفاصيل والتحذير الأمني ودليل إعادة تفعيل OTP خطوة بخطوة في قسم
**[Password Recovery: Current State & Future Reference](#password-recovery-current-state--future-reference)**.

## Password Recovery: Current State & Future Reference

### 1) الوضع الحالي: طلب يدوي بلا تخزين لكلمة المرور

بسبب قيود مزودي البريد المجانيين — وأهمها أن حساب **Resend** المجاني بهوية
`onboarding@resend.dev` لا يسلّم الرسائل إلا إلى بريد مالك الحساب نفسه — لا يمكن
للقالب اليوم إرسال رمز استعادة إلى مستخدمين حقيقيين. لذلك يُرسل المستخدم **بريده فقط**
لإنشاء طلب موافقة يدوي؛ عند الاعتماد تُولَّد كلمة مرور عشوائية وتُعرض مرة واحدة.

```text
الزائر (خارج الجلسة)                         المفوّض / owner / super_admin
──────────────────────                       ────────────────────────────────────
/login ← «نسيت كلمة المرور؟»                 /settings/system/password-resets
البريد فقط                                    طابور آمن: البريد + التاريخ + الحالة
  ↓ INSERT (RLS: مسموح للجميع)                 ↓ «اعتماد» ← توليد كلمة عشوائية
password_reset_requests (pending_approval)  → Edge Function admin-reset-password
                                                تحقق JWT + password_reset.manage
                                                ↓ reserve → GoTrue → finalize
                                                عرض مرة واحدة (PasswordRevealDialog)
                                                كلمة المرور لا تدخل SQL أو السجلات
```

1. **المستخدم يطلب:** من شاشة الدخول يُدخل بريده فقط. ينشأ صف بحالة
   `pending_approval` (سياسة RLS تسمح بالإدراج للجميع — الزائر هنا مجهول بلا جلسة)،
   وتظهر رسالة موحدة لأي بريد سواء كان مسجلاً أم لا، فلا يُستعمل النموذج لاستكشاف الحسابات.
2. **من يملك الصلاحية يرى أقل قدر من البيانات:** `owner` و`super_admin`، أو مستخدم
   مُفوّض بـ`password_reset.manage`، يقرأون View `password_reset_requests_safe` فقط؛
   أعمدته الأربعة هي `id`, `email`, `created_at`, `status`. لا يُمنح أي منهم قراءة
   مباشرة للجدول الأساسي.
3. **الاعتماد:** يختار المسؤول «اعتماد» في حوار تأكيد نصي بسيط (بلا أي حقل كلمة
   مرور). تُولِّد Edge Function كلمة مرور عشوائية مؤقتة (`generateTempPassword` —
   السياسة نفسها في الدعوات و`admin-set-password`) وتُمررها إلى GoTrue مباشرة؛
   لا تُرسل من المتصفح ولا إلى RPC أو قاعدة البيانات أو `audit_logs`، ولا تظهر
   إلا في رد النجاح مرة واحدة ليعرضها `PasswordRevealDialog` مع زر نسخ وتنبيه
   «لن تظهر مرة أخرى»، وبعد إغلاقه يُعاد تحميل الطابور. حماية إضافية: اعتماد طلب
   يخص حساب المالك الأصلي مرفوض (`42501 owner_protection`) حتى للمفوّضين.
4. **التنفيذ على الخادم:** `admin-reset-password` يتحقق من JWT ثم يستدعي RPCs مقفولة
   على `service_role` للتحقق من `password_reset.manage` وحجز الطلب، ثم يغيّر كلمة
   المرور عبر `supabase.auth.admin.updateUserById`. عند فشل GoTrue يُحرّر الحجز
   ليعاد المحاولة (وتُولَّد كلمة جديدة عندها)؛ عند النجاح ينتقل الطلب إلى `approved`. الرفض ينقل طلبًا
   `pending_approval` إلى `rejected` دون استلام كلمة مرور. كل انتقال نهائي يُسجل
   في `audit_logs` مع الحدث `password_reset.approved` أو `password_reset.rejected`.
5. **الحالات:** `pending_approval` قابل للمعالجة، و`awaiting_password` حجز قصير
   لعملية GoTrue، و`approved` و`rejected` حالتان نهائيتان. الترحيل
   `20261026000000_granular_role_delegation.sql` يحذف عمود `new_password` فعليًا؛
   الطلبات القديمة تبقى بلا كلمات مرور وتُولَّد لها كلمة عشوائية عند اعتمادها.

**النشر:** مؤتمت بالكامل — عند الدفع إلى `main` تنفّذ وظيفة `deploy_production`
(بيئة `Production` المحمية) الترحيل
`20261026000000_granular_role_delegation.sql` عبر `supabase db push --linked`
ثم تنشر `admin-reset-password` و`admin-user-capabilities` إلى جانب بقية الدوال؛
الترتيب مضمون: المخطط وRPCs تصل قبل الجسور. للنشر اليدوي/الطارئ:

```bash
supabase functions deploy admin-reset-password
supabase functions deploy admin-user-capabilities
```

> **تقليل البيانات:** كلمة المرور الجديدة لا تُخزَّن في أي جدول أو RPC؛ العمود القديم
> `new_password` أُزيل بترحيل forward-only. تظل سياسات قاعدة البيانات تمنع قراءة
> الجدول الأساسي من أدوار API، ويُتاح العرض الآمن فقط لمن يملك `password_reset.manage`.
> فهرس جزئي فريد يمنع تكرار الطلبات غير المنتهية للبريد الواحد. يُنصح بمسح الطلبات
> النهائية القديمة دوريًا وفق سياسة الاحتفاظ المعتمدة للمشروع.

### 2) المرجع المستقبلي: OTP & SMTP Setup

الكود البرمجي لتدفق **OTP** (رمز تحقق من 6 أرقام داخل التطبيق) **لم يُحذف** —
بقي كاملاً في `src/lib/passwordRecovery.ts`
(`requestPasswordRecoveryCode` / `verifyPasswordRecoveryCode` / `updatePassword`
وأكواد أخطائها الموحّدة) مع اختباراته في `passwordRecovery.test.ts`، وبقيت صفحة
`/reset-password` كمسار رابط احتياطي. هذا هو المرجع الجاهز لإعادة الاستعادة
الخدمية (Self-Service) بمجرد توفر بريد حقيقي.

**دليل إعادة تفعيل OTP خطوة بخطوة:**

1. **إعداد Custom SMTP في Supabase** — من **Authentication → Email → SMTP
   Settings** فعّل مزوّداً مخصصاً. مثال **Resend**:

   | الحقل        | القيمة                                     |
   | ------------ | ------------------------------------------ |
   | SMTP Host    | `smtp.resend.com`                          |
   | SMTP Port    | `465` (SSL) أو `587`                       |
   | Username     | `resend`                                   |
   | Password     | مفتاح Resend API (`re_...`)                |
   | Sender Email | `no-reply@your-domain.com` (نطاقك الموثّق) |
   | Sender Name  | اسم التطبيق                                |

   أضف سجلات SPF/DKIM لنطاقك، ثم جرّب **Send test email**.

2. 🚨 **تحذير هام — حساب Resend المجاني:** الإرسال من العنوان الافتراضي
   `onboarding@resend.dev` يسلّم **فقط إلى بريد مالك الحساب** (البريد المسجّل
   به في Resend) — أي رسالة استعادة لمستخدم آخر لن تصل. للإرسال إلى أي بريد
   يجب **توثيق نطاق (Domain) مخصص** في Resend (سجلات SPF/DKIM) أو **ترقية
   الخطة**. هذا القيد هو السبب المباشر لاعتماد التدفق اليدوي الحالي في
   القالب.

3. **تعديل قالب البريد في Supabase** — من **Authentication → Email Templates →
   Reset Password** اجعل القالب يعرض **الرمز** `{{ .Token }}` بدل زر الرابط
   `{{ .ConfirmationURL }}`، وتأكد من تفعيل خيار **Email OTP** حتى ترسل Auth
   رمزاً من 6 أرقام لا رابطاً. القالب الجاهز (Subject + نص + HTML) موجود في
   قسم «Authentication Setup» أدناه (1.1).

4. **إعادة تفعيل واجهة الـ OTP في صفحة الدخول** — `ForgotPasswordForm.tsx`
   كانت تنفّذ ثلاث خطوات داخل نفس البطاقة (البريد ← الرمز ← كلمة المرور
   الجديدة) باستدعاء دوال `passwordRecovery.ts` الباقية. أعد الخطوات الثلاث
   (من تاريخ git قبل التحويل، أو بربط
   `requestPasswordRecoveryCode` ← `verifyPasswordRecoveryCode` ←
   `updatePassword` مباشرة)، مع إبقاء الرد الموحّد المضاد لاستكشاف الحسابات.

5. **(اختياري) تقاعد التدفق اليدوي** — بعد التأكد من عدم وجود طلبات معلقة:
   أخفِ عنصر `settings-password-resets` من الشريط الجانبي، وأزل نموذج الطلب
   اليدوي، وأسقط الجدول بترحيل **جديد** إلى الأمام (لا تعدّل ترحيلاً قديماً):
   `drop table public.password_reset_requests;` — واحتفظ بـ RPCs الخدمة أو
   أسقطها معه في نفس الترحيل.

## Authentication Setup (إعداد المصادقة لكل بيئة)

هذا المستودع **قالب (Template)** يُنشر على دومين مختلف في كل بيئة، فلا يحتوي
الكود على أي رابط ثابت. استعادة كلمة المرور تعمل حالياً بـ **طلبات اعتماد
يدوي** لا تحتاج أي إعداد بريد أو نطاق (القسم السابق)، والخطوات أدناه هي ما
سيلزم **عند إعادة تفعيل OTP** مستقبلاً — مرة واحدة لكل مشروع (خطوات يدوية في
لوحة Supabase لا يمكن أتمتتها بأمان من الكود):

### 1) تفعيل البريد (SMTP) — وتأكّد أن الوارد رمز لا رابط

من **Authentication → Email** فعّل مزوّد SMTP مخصّصاً (مزوّده الافتراضي محدود
بعدد رسائل صغير وهوية بريد `@supabase.co`):

- **SMTP Host / Port / Username / Password** من مزوّد البريد.
- **Sender Email** و **Sender Name** باسم نطاقك (مثلاً `no-reply@your-domain.example.com`)
  مع سجلات SPF/DKIM حتى لا تذهب الرسائل إلى المهملات.
- بعد الحفظ جرّب **Send test email** للتأكد من الوصول.

> ⚠️ **تحقّق قبل الاعتماد:** افحص ما يصل فعلياً إلى المستخدم. التدفق يتوقّع
> **رمزاً من 6 أرقام**. إذا كانت رسالة الاستعادة التي تصلك تحتوي **رابطاً**، فمشروعك
> يُرسل روابط الاستعادة (السلوك الافتراضي لطلب الاستعادة)، وعليك تفعيل خيار
> **إرسال رمز تحقق (Email OTP)** من إعدادات البريد في لوحة Supabase حتى تكتمل
> خطوة التحقق داخل التطبيق.

> ملاحظة: إعدادات SMTP هذه تخص **رسائل المصادقة** (تأكيد البريد واستعادة كلمة
> المرور) داخل Supabase، وهي مختلفة عن نقل إشعارات النظام عبر عامل البريد
> `supabase/functions` الذي ميزة منفصلة.

### 1.1) قالب رسالة إعادة التعيين (Reset Password)

قالب Supabase الافتراضي لرسالة الاستعادة مصمَّم حول **الرابط**، بينما هذا التدفق
يدور حول **الرمز**. من **Authentication → Email Templates → Reset Password**،
استبدل الموضوع والنص بما يلي:

**Subject**

```text
رمز إعادة تعيين كلمة المرور — {{ .SiteURL }}
```

**Body (plain text)**

```text
مرحباً،

استلمنا طلباً لإعادة تعيين كلمة المرور الخاصة بحسابك.

رمز التحقق الخاص بك:
{{ .Token }}

أدخل هذا الرمز المكون من 6 أرقام في صفحة «نسيت كلمة المرور» داخل التطبيق،
ثم اختر كلمة مرور جديدة.

- الرمز صالح لمرة واحدة فقط.
- إن لم تطلب ذلك، تجاهل هذه الرسالة وستبقى كلمة مرورك كما هي.

—if you did not request a password reset, ignore this email and your
current password will stay active.
```

**Body (HTML)** — نفس المحتوى داخل قالب `<table>` بسيط، مع إبراز الرمز:

```html
<p>مرحباً،</p>
<p>استلمنا طلباً لإعادة تعيين كلمة المرور الخاصة بحسابك.</p>
<p style="font-size:24px;font-weight:700;letter-spacing:4px">{{ .Token }}</p>
<p>
  افتح <a href="{{ .SiteURL }}/login">صفحة تسجيل الدخول</a>، اختر «نسيت كلمة المرور؟»، وأدخل الرمز
  أعلاه لاختيار كلمة مرور جديدة.
</p>
<p>الرمز صالح لمرة واحدة فقط، وإن لم تطلب ذلك تجاهل هذه الرسالة.</p>
```

> **لماذا لا زر وصلة؟** الزر في القالب الافتراضي يقود إلى `{{ .ConfirmationURL }}`،
> وهو مسار الرابط القديم الذي أبقيناه كاحتياط فقط. اجعل الزر يفتح
> `{{ .SiteURL }}/login` — الرمز يُدخَل داخل التطبيق، فتبقى التجربة كاملة داخل
> صفحة واحدة ولا تعتمد على أي نطاق مُدرج.
>
> **تأكّد أن `{{ .Token }}` يتضمّن الرمز المكوّن من 6 أرقام**: إن استقبلت الوصلة
> في مكانه رابطاً كاملاً، فمشروعك لا يرسل رموزاً ⇒ فعّل **Email OTP** (القسم السابق).

### 2) (اختياري) وصلة الرابط القديمة + متغير `VITE_APP_URL`

التدفق الأساسي لا يحتاج أياً منهما. إن أردت إبقاء `/reset-password` وصلة
احتياطية (روابط أُرسلت سابقاً، أو نشر يفضّل الوصلة) فاضبط:

```bash
VITE_APP_URL=https://your-domain.example.com   # نطاق الإنتاج (بلا شرطة مائلة أخيرة)
```

ومن **Dashboard → Authentication → URL Configuration → Redirect URLs** أضف
`<origin>/reset-password` لكل نطاق تعرضه الواجهة. `env.appUrl` في
`src/lib/env.ts` يقرأ `VITE_APP_URL` ويرجع إلى `window.location.origin` إن لم
يُضبط، ويزيل الشرطة المائلة الأخيرة تلقائياً.

### 3) قائمة تحقق سريعة قبل اعتماد النشر

- [ ] SMTP مفعّل واختُبر بريد اختبار فعلياً.
- [ ] **رسالة الاستعادة تحتوي رمز 6 أرقام وليس رابطاً** (وإلا فعّل Email OTP).
- [ ] قالب **Reset Password** مُحدَّث حسب القسم 1.1 (يعرض الرمز ويشير إلى `/login`).
- [ ] دورة كاملة على حساب تجريبي: بريد ← رمز ← كلمة مرور جديدة ← الدخول بالجديدة.
- [ ] من `/login` ← «نسيت كلمة المرور؟» ثم اطلب عنوان **مسجّل** وآخر **غير مسجّل** —
      يجب أن تكون **الرسالة واحدة ومطابقة** في الحالتين (تحقّق أمني من عدم كشف
      وجود الحسابات).
- [ ] (اختياري) إن أبقينا وصلة الرابط: `VITE_APP_URL` مضبوط و
      `<origin>/reset-password` مُدرج في Redirect URLs.

## الاختبارات

`npm run test` — اختبارات Vitest عبر ملفات الواجهة والمصادقة، تغطي:

- الواجهة والمصادقة (Auth &amp; UI).
- نظام الصلاحيات والأدوار (RBAC &amp; Capabilities).
- نظام الإشعارات (Templates, Transports, RPCs).
- لوحة المؤشرات التنفيذية (RPC، الهوك، المكوّنات، بوابة القدرات).

كلها تدخل في `ci.yml` قبل البناء. تدفق Auth API المحلي في `supabase-migration.yml` يتحقق من أول تسجيل والثاني ومنع منح الدور عبر `service_role` مباشرةً.

**Database audit runs automatically in CI to prevent schema drift.**

خطوة `Run DB Audit` في `ci.yml` تشغّل `scripts/audit/database.mjs --reset-fixture` على
PostgreSQL 17 مُهيّأ خصيصاً لها (مقبس Unix في `.cache/live-audit/pg-socket`، منفذ 55432،
بلا أي بيانات اعتماد)، مع فحص جاهزية يسبق التشغيل. كانت هذه الخطوة يدوية سابقاً، فانحرف
عدد الهجرات المثبّت في السكربت من 24 إلى 27 دون أن يلاحظ أحد وتوقف التدقيق عند أول
تأكيد. ربطها بالـCI يحوّل أي انحراف في المخطط أو في سياسات RLS إلى بناء أحمر فوراً.
الدليل يُرفع كـartifact باسم `database-audit`.
